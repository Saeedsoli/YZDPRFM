# PWA — نصب روی گوشی و کار آفلاین

سرویس‌ورکر، صفحه آفلاین و دعوت نصب. مهم‌تر از همه: **چه چیزهایی
عمداً کش نمی‌شوند و چرا**.

---

## قاعده طلایی

> **هرگز قیمت یا موجودی کهنه نشان نده.**

این یک فروشگاه با پول واقعی است. سرویس‌ورکری که پاسخ API را کش
کند، ممکن است به مشتری قیمت دیروز یا کالای تمام‌شده را نشان دهد.
مشتری سفارش می‌دهد، سرور رد می‌کند، و اعتماد می‌رود.

**PWA بد از نداشتن PWA بدتر است.**

پس هیچ درخواست `/api/` کش نمی‌شود — نه با `stale-while-revalidate`،
نه با `network-first`، هیچ. در `sw.js` این مسیرها اصلاً از
سرویس‌ورکر رد نمی‌شوند؛ مرورگر مثل حالت عادی رفتار می‌کند.

---

## چه چیزی کش می‌شود

| دسته | راهبرد | چرا |
|---|---|---|
| فونت، CSS، JS، آیکن | `cache-first` | با `max-age=31536000 immutable` سرو می‌شوند |
| تصویر محصول | `cache-first` + سقف ۶۰ | نام فایل پایدار است، هرگز عوض نمی‌شود |
| صفحه HTML | network-first | تازه‌اش را بده؛ اگر شبکه نبود، نسخه ذخیره‌شده |
| صفحه آفلاین | در نصب | تا وقتی هیچ نسخه‌ای نداریم، این را نشان بده |

## چه چیزی هرگز کش نمی‌شود

```
/api/*        قیمت و موجودی زنده
/admin        داده مدیریتی
/account      اطلاعات شخصی
/invoice      نام و نشانی مشتری
/label        برچسب پستی
/checkout     مرحله پرداخت
/payment/*    نتیجه تراکنش
/login        نشست
/review-invite  توکن یک‌بارمصرف
```

به‌علاوه: **هر درخواست غیر GET**. سفارش و پرداخت هرگز دست
نمی‌خورند.

## آیکن‌ها — یک باگ واقعی که رفع شد

آیکن‌های قبلی با `purpose: "any maskable"` اعلام شده بودند، ولی
طراحی‌شان برای maskable مناسب نبود: قاب طلایی تا لبه می‌رفت.

اندروید آیکن maskable را به شکل دلخواه سازنده دستگاه می‌بُرد
(دایره، ذره‌بین، مربع گرد) و فقط دایره‌ای به شعاع ۴۰٪ از مرکز
«ناحیه امن» است.

**اندازه‌گیری: ۴۸٪ از محتوای آیکن بیرون ناحیه امن بود** — یعنی قاب
طلایی روی بیشتر گوشی‌های اندروید کاملاً بریده می‌شد.

راه‌حل استاندارد، دو آیکن جدا:

| آیکن | purpose | طرح | بیرون ناحیه امن |
|---|---|---|---|
| `icon-192.png` و `icon-512.png` | `any` | طرح کامل با قاب | ۷۵٪ (مشکلی نیست) |
| `icon-maskable-192.png` و `icon-maskable-512.png` | `maskable` | نقش کوچک، زمینه تمام‌صفحه | **۰٪** |

```bash
python3 scripts/make_pwa_icons.py    # ساخت + بررسی ناحیه امن
```

## هدرهای سرویس‌ورکر

`sw.js` مسیر اختصاصی در سرور دارد، نه سرو ساده از `public/`:

```
Cache-Control: no-cache, no-store, must-revalidate
Service-Worker-Allowed: /
```

**چرا `no-store` حیاتی است:** اگر مرورگر نسخه قدیمی `sw.js` را نگه
دارد، کاربر تا مدت‌ها نسخه تازه سایت را نمی‌بیند و **هیچ راهی برای
رفعش نداری**. این رایج‌ترین اشتباه در استقرار PWA است.

---

## 🐞 باگی که فقط با آزمون مرورگر پیدا شد

در صفحه آفلاین، **لوگوی برند شکسته نشان داده می‌شد** — در حالی که
فایل واقعاً در کش بود و `cache.match()` هم آن را پیدا می‌کرد.

علت: سرور برای تصاویر هدر `Vary: Accept` می‌فرستد (به‌خاطر ارائه
خودکار WebP). مرورگر با این هدر، پاسخ کش‌شده را با درخواست تازه
هم‌خوان نمی‌داند و **رد می‌کند** — حتی وقتی نشانی دقیقاً یکی است.

رفع: `cache.match(req, { ignoreVary: true })` در هر سه راهبرد.

دو تلاش اول اشتباه بودند (اول فکر کردم مشکل از مسیریابی است، بعد
از ترتیب بررسی کش). فقط ردیابی درخواست‌های ناموفق در مرورگر واقعی
علت را نشان داد.

## دعوت نصب

بنر پایین صفحه، نه پاپ‌آپ وسط:

- فقط وقتی ظاهر می‌شود که مرورگر بگوید نصب ممکن است
  (`beforeinstallprompt`)
- اگر کاربر رد کند، **تا ۳۰ روز دیگر پرسیده نمی‌شود**
- در حالت نصب‌شده (`display-mode: standalone`) هرگز دیده نمی‌شود
- روی موبایل بالای نوار خرید می‌نشیند تا تداخل نکند

این همان تفاوت میان دعوت و مزاحمت است. پاپ‌آپ خودکار هنگام ورود،
همان الگویی است که در تحلیل رقابتی ردش کردیم.

---

## میان‌برها

سه میان‌بر در manifest که با فشار طولانی روی آیکن ظاهر می‌شوند:

| میان‌بر | مسیر |
|---|---|
| کوییز رایحه | `/quiz` |
| سمپل ۳ میل | `/samples` |
| پیگیری سفارش | `/track` |

هر سه با `utm_source=pwa_shortcut` تا در تحلیل داخلی قابل تفکیک
باشند.

## اثر بر کارایی

ثبت سرویس‌ورکر **پس از رویداد `load` و در زمان بیکاری** انجام
می‌شود. نخستین بازدید نباید کندتر شود؛ FCP این سایت ۰٫۲۶ ثانیه است
و نگه داشتنش ارزش دارد.

اگر ثبت شکست بخورد، سایت کاملاً کار می‌کند — کل بلوک در `catch`
بی‌صدا است.

## آزمون

```bash
node scripts/test_pwa.js            # ۵۳ بررسی — پیکربندی
python3 scripts/test_pwa_browser.py # رفتار واقعی در مرورگر
```

`test_pwa.js` پیکربندی را می‌سنجد: manifest کامل است؟ آیکن maskable
ناحیه امن دارد؟ `sw.js` هدر `no-store` دارد؟

`test_pwa_browser.py` **رفتار** را می‌سنجد و مهم‌ترین ادعا را
اثبات می‌کند:

```
✓ 🔴 هیچ پاسخ API کش نشده
✓ 🔴 API آفلاین داده کهنه نمی‌دهد   — TypeError: Failed to fetch
✓ هیچ صفحه حساسی کش نشده
✓ صفحه دیده‌شده آفلاین باز می‌شود
✓ صفحه دیده‌نشده به صفحه آفلاین می‌رسد
```

خط دوم مهم‌ترین است: درخواست API آفلاین **شکست می‌خورد** (درست)
نه اینکه داده کهنه برگرداند (فاجعه).

## به‌روزرسانی نسخه

با هر تغییر در فهرست پوسته، `CACHE_VERSION` در `sw.js` بالا برود.
کش قدیمی در رویداد `activate` خودکار پاک می‌شود.

نسخه فعلی: `yazd-v3`

نسخه تازه بی‌سر و صدا فعال می‌شود — بدون پیام «نسخه جدید موجود
است». کاربر فقط می‌خواهد عطر بخرد.

---

## آنچه ساخته نشد

**همگام‌سازی پس‌زمینه (Background Sync)** برای ثبت سفارش آفلاین.
وسوسه‌انگیز است ولی خطرناک: سفارشی که ساعت‌ها بعد ارسال شود، با
قیمت و موجودی آن لحظه سنجیده می‌شود و ممکن است رد شود — بدون اینکه
مشتری بداند. تجربه بدتری از «الان نمی‌شود، بعداً امتحان کنید» است.

**اعلان فشاری (Push Notification)** نیاز به سرور اعلان و مجوز
کاربر دارد. برای فروشگاهی که هنوز پیامک راه نیفتاده، زودهنگام است.
