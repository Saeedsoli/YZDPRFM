# قیمت‌گذاری بر پایه دلار — گام اول

> **این سند زنده است.**
>
> وضعیت امروز: **فقط نگهداری عدد.** فرمول محاسبه خودکار هنوز
> پیاده نشده و منتظر دریافت آن از مالک است.

---

## هدف نهایی

فروشگاه فرمولی برای قیمت‌گذاری دارد که به نرخ دلار وابسته است —
وزن اسانس، قیمت دلاری، و هزینه‌های دیگر. هدف: **با تغییر نرخ ارز،
قیمت تومانی همه محصولات خودکار به‌روز شود.**

امروز قیمت‌ها دستی وارد می‌شوند. با ۱۴٬۷۷۷ واریانت، هر تغییر نرخ
یعنی کاری که عملاً انجام نمی‌شود — و قیمت‌ها از واقعیت عقب می‌مانند.

---

## آنچه امروز هست

یک فیلد در پنل: **قیمت پایه ($)** کنار قیمت تومانی، در جدول
ویرایش محصول.

```
پنل → محصولات → ویرایش → ستون «قیمت پایه ($)»
```

خالی گذاشتنش یعنی «هنوز وارد نشده». عدد اعشاری می‌پذیرد.

---

## چهار تصمیم طراحی

### ۱) نوع `REAL` نه `INTEGER`

قیمت تومان عدد صحیح است چون ریال اعشار ندارد. ولی قیمت دلاری
اسانس معمولاً اعشاری است — ۱۲٫۵ دلار برای ۱۰ گرم.

اگر گرد می‌کردیم، خطا در فرمول نهایی **تکثیر** می‌شد: یک اختلاف
نیم‌دلاری در پایه، ضرب در وزن و نرخ ارز، می‌تواند ده‌ها هزار
تومان اختلاف در قیمت نهایی بسازد.

### ۲) `NULL` جدا از صفر

امروز هیچ محصولی قیمت دلاری ندارد. اگر پیش‌فرض صفر می‌گذاشتیم،
بعداً نمی‌شد فهمید «صفر یعنی رایگان» یا «هنوز وارد نشده».

```
NULL  →  نامشخص، فرمول روی این محصول اجرا نشود
0     →  واقعاً رایگان (مثلاً سمپل هدیه)
```

رشته خالی در پنل به `NULL` تبدیل می‌شود، نه صفر.

### ۳) 🔴 به مشتری نمی‌رود

قیمت دلاری **پایه محاسبه** است، نه اطلاعات محصول. اگر در پاسخ
عمومی بیاید، هر بازدیدکننده‌ای می‌تواند حاشیه سود را حساب کند:

```
قیمت تومانی ÷ (قیمت دلاری × نرخ روز) = ضریب سود
```

`attachVariants` فهرست سفید دارد و این میدان را نمی‌دهد. پس
پنل مسیر خودش را گرفت:

```
GET /api/admin/products/:slug     ← قیمت دلاری دارد
GET /api/products/:slug           ← ندارد
```

آزموده شده: در `/api/products`، `/api/products/:slug` و
`/api/showcase` هیچ اثری از `price_usd` نیست.

### ۴) مجوز `products.price`

انباردار محصول را می‌بیند و موجودی را عوض می‌کند، ولی قیمت
دلاری را **نه می‌بیند نه می‌تواند بگذارد**.

نکته پیاده‌سازی: در مسیر خواندن، نبودِ مجوز **خطا نیست** — فقط
آن میدان حذف می‌شود. پس `can()` صدا زده نمی‌شود (که خودش ۴۰۳
می‌فرستد)، بلکه مجوز مستقیم بررسی می‌گردد.

## اعتبارسنجی

| ورودی | نتیجه |
|---|---|
| `12.5` | ✅ ذخیره می‌شود |
| `0.075` | ✅ اعشار ریز هم حفظ می‌شود |
| `0` | ✅ صفر معتبر است |
| `''` | ✅ به `NULL` می‌رود |
| `-5` | ❌ عدد منفی |
| `999999` | ❌ سقف ۱۰۰٬۰۰۰ دلار |
| `abc` | ❌ متن |

**چرا سقف:** گران‌ترین اسانس جهان زیر ۱۰٬۰۰۰ دلار در کیلوست.
عدد بزرگ‌تر یعنی اشتباه تایپی — و چون قرار است پایه محاسبه
خودکار شود، آن اشتباه در قیمت هزاران محصول تکثیر می‌شود.

## ثبت در سابقه

هر تغییر قیمت دلاری در `audit_log` با مقدار پیش و پس ثبت می‌شود،
زیر همان کنش `products.price`:

```json
{ "usd": [null, 12.5] }
```

## آنچه باقی است

**فرمول.** مالک گفته بعداً می‌فرستد. چیزهایی که هنگام دریافتش
باید روشن شود:

| پرسش | چرا مهم است |
|---|---|
| نرخ دلار از کجا می‌آید؟ | دستی در تنظیمات، یا API؟ |
| هر واریانت وزن جدا دارد؟ | یا از `volume_ml` حساب می‌شود؟ |
| هزینه‌ها ثابت‌اند یا درصدی؟ | بطری، جعبه، دستمزد |
| گرد کردن چطور باشد؟ | تا هزار تومان؟ ده هزار؟ |
| قیمت دستی اولویت دارد؟ | اگر مدیر عددی دستی گذاشت، فرمول بازنویسی‌اش کند؟ |

آخری مهم‌ترین است: بدون آن، یک محاسبه خودکار می‌تواند قیمت‌های
دستی‌تنظیم‌شده را پاک کند.

### دو خطای آزمون که در مسیر اصلاح شد

**۱) `makeStaff` شیء برمی‌گرداند، نه رشته توکن.** نسخه اول آن را
مستقیم به‌عنوان توکن فرستاد؛ سرور هدر بی‌معنا گرفت و ۴۰۳ داد —
که تصادفاً شبیه «مرز دسترسی کار می‌کند» بود. **سبزِ توخالی
خطرناک‌تر از قرمز است.**

**۲) پاک‌سازی فقط در پایان کافی نبود.** اگر اجرای قبلی نیمه‌کاره
تمام می‌شد، کارمند آزمایشی می‌ماند و ساخت دوباره ۴۰۰ می‌داد.
حالا پیش از ساخت هم پاک می‌شود.
