> **این سند زنده است** — همیشه وضعیت امروز را می‌گوید.
> نسخه پیشین این سند درباره Vendure بود و پس از تصمیم به پیاده‌سازی

## ۱. تصمیم بنیادی

**Node.js خالص + SQLite، بدون فریم‌ورک و بدون وابستگی خارجی جز یک کتابخانه.**

### چرا نه Vendure یا MedusaJS؟

اسناد اولیه پروژه Vendure را پیشنهاد می‌دادند. آن مسیر انتخاب نشد:

| معیار | Vendure/Medusa | پیاده‌سازی فعلی |
|---|---|---|
| وابستگی npm | ۸۰۰+ بسته | **۱ بسته** |
| زمان استقرار | ۳ تا ۸ دقیقه | **۱۵ ثانیه** |
| مصرف حافظه | ۴۰۰ تا ۸۰۰ مگابایت | حدود ۸۰ مگابایت |
| نیاز به PostgreSQL جدا | بله | خیر |
| کل کد قابل‌فهم | ده‌ها هزار خط | **۳٬۴۵۵ خط** |

برای فروشگاهی با ۲٬۱۰۶ محصول و ترافیک متوسط، لایه‌های انتزاعی
Vendure هزینه‌ای بدون بازده بودند. هر خط این سیستم قابل خواندن و
تغییر است.

### چرا نه Next.js؟

صفحات با HTML و جاوااسکریپت ساده ساخته شدند. مشکل معمول این روش
— نامرئی بودن برای گوگل — با تزریق متادیتا سمت سرور حل شد
(`src/seo.js`). نتیجه: صفحه اصلی **۴٬۷۵۸ بایت** با gzip در
**۳.۵ میلی‌ثانیه**؛ چیزی که با bundle یک فریم‌ورک به‌سختی ممکن بود.

## ۴. لایه داده

### چرا SQLite؟

- تک‌فایل، بدون سرویس جداگانه → روی Liara فقط یک دیسک لازم است
- تراکنش ACID واقعی — **تست شد**: دو سفارش همزمان برای آخرین موجودی،
  یکی موفق و دومی رد شد
- حالت WAL برای خواندن همزمان
- کوئری فیلتر روی ۲٬۱۰۶ محصول: **۱ میلی‌ثانیه**

محدودیت واقعی SQLite نوشتن همزمان است. برای فروشگاهی با چند ده
سفارش روزانه، هرگز به آن نمی‌رسیم. اگر رسیدیم، مهاجرت به
PostgreSQL تنها تغییر `db.js` است چون بقیه ماژول‌ها SQL خام نمی‌بینند.

اسکریپت دستی ندارد. در اولین اجرا، ۲٬۱۰۶ محصول از فایل seed
منتقل می‌شود.

## ۵. تصمیم‌های کلیدی

### قیمت هرگز از کاربر خوانده نمی‌شود

```js
// validateCart — قیمت از دیتابیس، نه از درخواست
const row = stmt.get(item.sku);
const lineTotal = row.price_toman * qty;
```

تست: کاربر `price_toman: 1` فرستاد، سرور `4,700,000` محاسبه کرد.

### SKU با شناسه عددی، نه حروف برند

فرمول اولیه سه حرف اول برند را می‌گرفت، پس Carolina و Caron و
Cartier همه `CAR` می‌شدند — **۱٬۲۶۷ تصادم**. فرمول به
`YZD-{شماره محصول}-{نوع}-{حجم}` تغییر کرد. حالا هر ۱۴٬۷۴۲ SKU یکتاست.

این باگ فقط چون SQLite قید `UNIQUE` دارد کشف شد؛ با JSON هرگز
معلوم نمی‌شد.

### نشست در دیتابیس، نه حافظه

Liara روزانه چند بار ری‌استارت می‌کند. با `Map` در حافظه، هر بار
تمام کاربران خارج می‌شدند. جدول `sessions` این را حل کرد —
تست شد: دو فرآیند Node جدا، توکن معتبر ماند.

### قیمت اعلام‌شده = قیمت پرداختی

هیچ محاسبه مالیاتی یا مبلغ اضافه دیگری در سامانه وجود ندارد.
قیمت نمایش‌داده‌شده همان مبلغ نهایی است:

```
جمع کالاها − تخفیف + ارسال = مبلغ پرداختی
```

فاکتور هم دقیقاً همین سه سطر را چاپ می‌کند — نه سطری بیشتر.

### درگاه و پیامک قابل‌تعویض

هر دو پشت واسط یکسان‌اند. تغییر ارائه‌دهنده = یک متغیر محیطی،
بدون دست زدن به کد.

## ۷. عملکرد

| مسیر | خام | gzip | زمان |
|---|---|---|---|
| صفحه اصلی | ۱۴٬۵۵۸ | ۴٬۷۵۸ | ۳.۵ms |
| API کاتالوگ | ۱۱٬۸۵۰ | ۱٬۹۶۵ | ۴ms |
| sitemap (۲٬۱۱۴ لینک) | ۲۲۷٬۲۸۶ | ۹٬۹۷۲ | ۴ms |

**سه بهینه‌سازی مؤثر:**

۱. **gzip** روی پاسخ بالای ۱KB — تا ۹۶٪ کاهش
۲. **پاسخ سبک کاتالوگ** — متغیرها فقط با `?full=1`
۳. **WebP خودکار** بر اساس هدر `Accept` — ۵۳٪ سبک‌تر

### جستجو

ستون `search_blob` همه فیلدها را یکجا دارد، با یکسان‌سازی فارسی:
حذف اعراب، تبدیل ی/ک عربی، نیم‌فاصله.

```
کرید = کرِید = كريد  →  هر سه ۲۶ نتیجه، زیر ۵ms
```

## ۱۰. مسیر رشد

| نشانه | اقدام |
|---|---|
| بیش از ۵۰ سفارش همزمان | مهاجرت `db.js` به PostgreSQL |
| کاتالوگ بالای ۲۰٬۰۰۰ | SQLite FTS5 به‌جای LIKE |
| نیاز به چند ادمین | جدول `admins` با نقش |
| ترافیک بالا | CDN برای `public/images` |

هیچ‌کدام امروز لازم نیست. معماری فعلی برای مقیاس هدف طراحی شده،
نه برای مقیاسی که شاید هرگز نرسد.
