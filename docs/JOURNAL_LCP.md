# بهبود LCP صفحه مجله — ۵٫۲۲ به ۲٫۸۱ ثانیه

آخرین مورد ⚠️ باقی‌مانده از بنچمارک ۱۴۰۵/۰۵/۰۶ بود. گزارش آن روز
نوشته بود:

> «حل کامل نیازمند رندر سمت سرور برای محتوای اولیه است که تغییر
> معماری می‌خواهد، نه بهینه‌سازی.»

این نتیجه‌گیری **نیمی درست بود**: رندر سمت سرور لازم بود، ولی نه
برای کل صفحه — فقط برای یک بلوک.

---

## نتیجه اندازه‌گیری‌شده

```
شرایط: ۳G کند · ۴۰۰kbps · ۴۰۰ms تأخیر · موبایل ۳۹۰px

              پیش      پس       تغییر
LCP         ۵٬۲۱۶ms  ۲٬۸۰۸ms   −۴۶٪
CLS           ۰٫۰۰۳    ۰         ✓
FCP         ۱٬۳۰۸ms  ۱٬۴۹۲ms   +۱۸۴ms
```

> FCP کمی بدتر شد چون HTML سنگین‌تر است (بلوک مقاله شاخص
> داخلش آمده). معامله آگاهانه‌ای است: ۱۸۴ میلی‌ثانیه دیرتر
> اولین رنگ، در برابر ۲٬۴۰۸ میلی‌ثانیه زودتر دیدن محتوای اصلی.

---

## سه گام، هر کدام با اندازه‌گیری

### گام ۰: فهمیدن مسئله

اول ابزار ساختم (`scripts/trace_lcp.py`) که می‌گوید **کدام عنصر**
LCP است و زنجیره درخواست‌ها چطور پیش می‌رود. بدون این، بهینه‌سازی
حدس بود.

```
    9 →   442ms  document   /journal
  472 →   881ms  stylesheet /assets/theme.css
  529 →  1323ms  script     /assets/app.js
 1302 →  4574ms  font       Vazirmatn-Bold.woff2
 1305 →  4603ms  font       Vazirmatn-ExtraBold.woff2
 1305 →  4632ms  font       Vazirmatn-Regular.woff2
 1324 →  1820ms  fetch      /api/articles
 2585 →  3107ms  image      family-woody.webp   ◀ LCP
```

تصویر LCP در **۲٬۵۸۵** شروع می‌شد، در حالی که HTML در ۴۴۲
آماده بود. بیش از دو ثانیه انتظار محض.

آزمون کنترلی: با مسدود کردن فونت‌ها، LCP به ۳٬۶۸۴ رسید — یعنی
سه فونت (۸۷KB) تنها **۱٬۴۴۰ میلی‌ثانیه** از LCP را می‌خوردند.

### گام ۱: preload از سمت سرور

سرور می‌داند تازه‌ترین مقاله کدام است، پس می‌تواند تصویرش را در
`<head>` اعلام کند — همان الگویی که برای صفحه محصول به کار رفته
بود.

```
۵٬۲۱۶ → ۳٬۵۴۰ms
```

تصویر حالا در ۴۷۰ms شروع می‌شود به‌جای ۲٬۵۸۵.

### گام ۲: چرا هنوز ۳٫۵ ثانیه؟

ردیابی **نامزدهای LCP** پاسخ داد:

```
 1480ms    1,989px²  <?>
 1520ms    4,158px²  <DIV.announce>
 2532ms    7,859px²  <H1>
 2648ms   27,612px²  <P>
 3584ms   68,121px²  <IMG>  brand-amouage.webp
```

تصویر در **۹۱۰ms دانلود** شده بود ولی در **۳٬۵۸۴ رندر** می‌شد.
دلیل: تگ `<img>` را جاوااسکریپت پس از پاسخ `/api/articles`
می‌ساخت.

**درس:** `preload` نیمی از مسئله را حل می‌کند — فایل زودتر
می‌آید ولی جایی برای نشستن ندارد.

### گام ۳: رندر سمت سرور فقط برای یک بلوک

`seo.js` تابع `featureHTML()` گرفت که HTML مقاله شاخص را
می‌سازد و سرور آن را جای `<div id="feature">` می‌گذارد.

```
۳٬۵۴۰ → ۲٬۸۰۸ms
```

کل صفحه SSR نشد — فقط ۲۰ خط HTML. تغییر معماری لازم نبود.

### گام ۴: خالی کردن مسیر بحرانی

`/api/notice` و `/api/auth/me` روی مسیر بحرانی بودند و با تصویر
LCP بر سر پهنای باند رقابت می‌کردند. هیچ‌کدام برای دیدن محتوا
لازم نیستند:

```js
function whenIdle(fn, timeout = 2000) {
  if (typeof requestIdleCallback === 'function') requestIdleCallback(fn, { timeout });
  else setTimeout(fn, 200);
}
```

سقف دو ثانیه گذاشته شد تا روی دستگاه همیشه‌مشغول هم اجرا شود.
سافاری `requestIdleCallback` ندارد، پس `setTimeout` جایگزین است.

## دام اصلی: هماهنگی preload با آنچه مرورگر می‌خواهد

اگر نشانی `preload` با نشانی `<source>` یکی نباشد، مرورگر **دو
فایل** دانلود می‌کند و LCP **بدتر** از حالت بدون preload می‌شود.
یک بار در صفحه محصول همین شد: ۶٫۳۵ → ۷٫۱۶ ثانیه.

سه محافظ گذاشته شد:

۱. **`coverOf()` در `seo.js`** — نسخه سرور، با هشدار صریح که
   باید با نسخه `journal.html` یکی بماند
۲. **`data-slug`** — فرانت اگر ببیند همان مقاله رندر شده، دست
   نمی‌زند. بدون این، جاوااسکریپت تگ آماده را دور می‌انداخت و
   از نو می‌ساخت
۳. **آزمون خودکار** — `test_journal_lcp.js` مقایسه می‌کند که
   `preload` و `source` دقیقاً یکی باشند

## باگی که در مسیر پیدا شد: ترتیب غیرقطعی مقالات

هر پنج مقاله اولیه `created_at` **یکسان** دارند. `ORDER BY
created_at DESC` بدون شکننده تساوی، ترتیب تضمین‌شده نمی‌دهد —
یعنی سرور می‌توانست تصویر مقاله‌ای را preload کند که فرانت
شاخص نمی‌دانست.

```sql
-- پیش
ORDER BY created_at DESC
-- پس
ORDER BY created_at DESC, id
```

در هر دو جا (API و SSR) اصلاح شد. هیچ علامتی نداشت جز LCP
گاه‌به‌گاه بدتر.

## باگ بصری: «۷ دقیقه» که «۷۰ دقیقه» خوانده می‌شد

در بزرگ‌نمایی ۳ برابر دیده شد:

```
راهنمای خرید ۷ · دقیقه     ← چشم می‌خواند «۷۰ دقیقه»
```

نقطه‌وسط `·` نویسه **خنثی** است و جهتش را از همسایه می‌گیرد.
بین متن فارسی و رشته‌ای که با رقم شروع می‌شود، مرورگر آن را
بعد از عدد می‌گذارد.

`<bdi>` جواب نداد — نه دور عدد، نه شامل جداکننده — چون نویسه
خنثی داخل بلوک RTL باز هم به انتها می‌رود.

**راه‌حل:** جداکننده اصلاً در جریان متن نباشد.

```css
.sep { display: inline-block; width: 1.5em; text-align: center; }
.sep::before { content: '|'; opacity: .38; }
```

خط عمودی هم انتخاب شد چون نقطه‌وسط در ۱۱px با رقم «۰» اشتباه
گرفته می‌شود. در `journal.html`، `article.html` و `seo.js`
اعمال شد.

> این باگ را هیچ آزمون API نمی‌گرفت. فقط عکس با
> `device_scale_factor=3`.

## چه چیزی حل نشد

**فونت‌ها هنوز ۱٬۴۴۰ میلی‌ثانیه می‌گیرند.** سه فایل ۲۹KB که از
۱٬۵۰۰ تا ۴٬۹۰۰ پهنای باند را اشغال می‌کنند.

گزینه‌هایی که بررسی و **رد** شدند:

| گزینه | چرا رد شد |
|---|---|
| حذف یک وزن فونت | هویت بصری برند آسیب می‌بیند |
| `preload` فونت | قبلاً آزموده شد؛ LCP را بدتر کرد |
| زیرمجموعه‌سازی بیشتر | فونت‌ها از قبل subset شده‌اند (۲۹KB) |
| فونت متغیر (variable) | نسخه متغیر وزیرمتن ~۹۰KB است — بدتر |

`font-display: optional` از قبل تنظیم است، یعنی متن **بدون
انتظار** با فونت جایگزینِ هم‌ابعاد نمایش داده می‌شود و فونت
اصلی وقتی رسید جایگزین می‌شود. پس تأثیرش روی تجربه کاربر
کمتر از عددِ خام است.
