# تفکیک `server.js` — گام اول

## چرا

`server.js` به **۴٬۳۵۱ خط** رسیده بود و بزرگ‌ترین ریسک نگهداری
پروژه شده — بزرگ‌تر از انتخاب زبان یا فریم‌ورک.

```
پیش   server.js  ۴٬۳۵۱ خط · ۱۰۳ شرط مسیر
پس    server.js  ۳٬۷۹۲ خط · ۸۷ شرط مسیر   (−۱۳٪)
      routes/    ۷۳۷ خط در ۳ ماژول
```

---

## الگوی به‌کاررفته

مسئله: همه مسیرها داخل **یک closure** بودند و به هفت متغیر محلی
وابسته‌اند:

```js
sendJSON · sendBody · who · logAudit · can · requireAdmin · parsed
```

پس جابه‌جایی متن کافی نبود. هر ماژول یک شیء `ctx` می‌گیرد و
`Promise<boolean>` برمی‌گرداند:

```js
// src/routes/articles.js
async function handle(ctx) {
  const { method, pathname, sendJSON, can, db } = ctx;

  if (method === 'GET' && pathname === '/api/articles') {
    sendJSON(200, { … });
    return true;    // رسیدگی شد
  }
  return false;     // مسئول این مسیر نیستم
}
```

```js
// src/server.js
if (await routeArticles.handle({ method, pathname, sendJSON, can, db, … })) return;
```

## باگ دوم: ممیزی که کور شد

`audit_permissions.js` فقط `server.js` را اسکن می‌کرد. با
انتقال مقالات به `routes/`، مجوزهای `content.write` و
`content.delete` **«بدون بررسی» گزارش شدند** — در حالی که
سالم بودند.

```diff
- const src = fs.readFileSync('src/server.js', 'utf8');
+ const src = [server.js, ...همه فایل‌های src/routes/].join('\n');
```

> ممیزی‌ای که با جابه‌جایی کد کور شود، **بدتر از نبودنش است** —
> چون سبز بودنش دروغ می‌گوید.

این اصلاح ممیزی را در برابر تفکیک‌های آینده هم مقاوم کرد.

## ابزار تازه — استخراج وابستگی با تحلیل نحوی

درس تلخ تفکیک RBAC: regex چهار وابستگی را جا انداخت
(`otp`, `notify`, `faNum`, `getToken`) چون
`otp.normalizeMobile()` را به‌عنوان استفاده از `otp` نشناخت.

`scripts/lib/extract_deps.js` این را حل می‌کند: توکن‌سازی آگاه از
**رشته، کامنت، الگوی قالبی، ویژگی شیء و کلید object literal**.

آزمون روی همان الگوی جاافتاده:

```
ورودی : otp.normalizeMobile(m); notify.orderPaid(o);
        faNum(5) + getToken(req)
خروجی : faNum, getToken, m, notify, o, otp, req   ✓
```

روی بلوک واقعی: **۱۶ وابستگی، صفر جاافتاده، صفر بی‌مصرف.**

> ولی این ابزار **جایگزین آزمون نیست**. فهرست نامزد می‌دهد؛ تنها
> تأیید واقعی، اجرای هر مسیر است — که یافته بعدی ثابتش کرد.

## 🔴 باگی که آزمون گرفت — و بدون آن فاجعه بود

نخستین اجرای `test_admin_catalog.js`: **۱۷ بررسی ناموفق از ۲۵**،
همه با `status 0`.

لاگ سرور:

```
Error [ERR_HTTP_HEADERS_SENT]: Cannot write headers after
they are sent to the client
    at sendBody (src/server.js:594)
```

### علت

در `server.js` الگوی `return sendJSON(...)` یعنی «پاسخ بده و از
handler خارج شو». اما `sendJSON` مقداری برنمی‌گرداند، پس در ماژول
`undefined` می‌شود — که **falsy** است.

نتیجه زنجیره‌ای:

1. ماژول پاسخ می‌فرستد ولی `false` برمی‌گرداند
2. سرور فکر می‌کند مسیر رسیدگی نشده، ادامه می‌دهد
3. در انتها ۴۰۴ روی همان پاسخ می‌نویسد
4. خطا **بیرون از try/catch** رخ می‌دهد → **کل فرآیند می‌میرد**

یعنی نخستین درخواست به هر یک از این شش مسیر، **کل سایت را پایین
می‌آورد**.

### چرا خطرناک بود

- `node -c` سبز ✓
- سرور بالا آمد ✓
- تحلیل وابستگی کامل بود ✓
- **همه‌چیز درست به‌نظر می‌رسید**

### رفع

`sendJSON` پوششی در ماژول:

```js
const sendJSON = (code, data) => { ctx.sendJSON(code, data); return true; };
```

دو راه بود: ۱۳ نقطه را دستی به دو خط تبدیل کنیم (پرخطا و پرنویز)،
یا پوششی که همان الگو را معنادار کند. راه دوم خواناتر است و فرصت
فراموشی نمی‌دهد.

> **درس:** الگوی `ctx` ظاهراً ساده است، ولی **قرارداد بازگشتی**
> بخش نامرئی آن است. هر ماژول تازه باید صریحاً بررسی شود که هر
> مسیر موفق `true` برمی‌گرداند.

## 🎯 درس گام ۱ کار کرد

باگ `ERR_HTTP_HEADERS_SENT` که در گام ۱ کل سایت را می‌کشت، اینجا
**اصلاً رخ نداد** — چون `sendJSON` پوششی از ابتدا گذاشته شد.

ولی همان تله در **شکل تازه‌ای** ظاهر شد:

```js
return res.end();     // پاسخ استریمی CSV → undefined → falsy
```

مسیر CSV مستقیم روی `res` می‌نویسد و `sendJSON` صدا نمی‌زند، پس
پوشش کمکش نمی‌کرد. رفع:

```js
res.end();
return true;      // پاسخ استریمی — sendJSON صدا زده نشد
```

> **درس:** هر مسیری که پاسخ را از راهی جز `sendJSON` می‌فرستد،
> باید جداگانه بررسی شود. آزمون حالا این را صریحاً می‌سنجد.

## تله «پاسخ غیر sendJSON» — شکل سوم و چهارم

الگو ادامه دارد و هر گام شکل تازه‌ای می‌گیرد:

| گام | شکل |
|---|---|
| ۱ | `return sendJSON(...)` → پوشش |
| ۲ | `return res.end()` (CSV) |
| ۴ | `return fs.createReadStream(full).pipe(res)` |
| ۴ | `return;` خالی پس از `stream.pipe(res)` |

هر چهار مورد `undefined` می‌دهند که falsy است. در این گام هر دو
مسیر پشتیبان **استریم فایل** می‌فرستند، پس پوشش `sendJSON`
کمکشان نمی‌کرد.

> **قاعده‌ای که از این پس در هر گام بررسی می‌شود:**
> هر مسیری که پاسخ را از راهی جز `sendJSON` می‌فرستد، باید
> صریحاً `return true` داشته باشد. جستجوی `return;` خالی و
> `pipe(res)` بخش ثابت بازبینی شد.
