**تاریخ:** تیر و مرداد ۱۴۰۵ · **تغییرنامه** — ثبت تاریخی، به‌روز نمی‌شود

> **یادداشت مسیرها:** پس از آماده‌سازی مخزن گیت، منابع خام
> جابه‌جا شدند. مسیرهای این سند مربوط به ساختار آن زمان‌اند:
> `uploads/logo.png` → `source/brand/logo.png` ·
> `assets/product-nologo/` → `source/product-images/` ·
> `assets/fonts-original/` → `source/fonts/`

این سند کارهای انجام‌شده در دور بازطراحی UI/UX را ثبت می‌کند: چه چیزی
عوض شد، **چرا** عوض شد، و هر باگ چطور کشف و راستی‌آزمایی شد.

> هر ادعای «رفع شد» در این سند با یک تست اجراشده همراه است. اگر تستی
> نبوده، نوشته‌ام «راستی‌آزمایی نشده».

## باگ‌های کشف‌شده

### ۱. لینک‌های فیلتر کاتالوگ کار نمی‌کردند 🔴

**علائم:** کلیک روی هر برند در صفحه `brands.html`، مسیر راهنمای صفحه
محصول، یا جستجوی صفحه ۴۰۴ کاربر را به کاتالوگ کامل ۲,۱۰۶ تایی می‌برد.

**ریشه:** `index.html` هرگز `location.search` را نمی‌خواند. API از قبل
پارامتر `brand` را پشتیبانی می‌کرد.

```bash
# تأیید اینکه API سالم بود:
curl -s "localhost:3000/api/products?brand=پنهالیگونز&limit=2"
# → total: 28 ✓

# اما صفحه اصلی:
curl -s "localhost:3000/?brand=test" | grep -c "location.search"
# → 0  ✗
```

**رفع:** توابع `readURL()` و `writeURL()` در `index.html`. حالا وضعیت
دوطرفه با نشانی صفحه همگام است — لینک قابل اشتراک شد و دکمه بازگشت
مرورگر کار می‌کند.

**فایل:** `public/index.html`

---

### ۲. سبد خرید هرگز با سرور همگام نمی‌شد 🔴

**علائم:** کاربر سبد را پر می‌کرد، روزها بعد برمی‌گشت، فرم تسویه را کامل
پر می‌کرد، و **در لحظه پرداخت** با «موجودی کافی نیست» روبه‌رو می‌شد.

**ریشه:** قیمت و موجودی از `localStorage` خوانده می‌شد. سرور امن بود
(قیمت را از دیتابیس می‌گرفت) ولی کاربر تا آخرین لحظه بی‌خبر می‌ماند.

**رفع:** مسیر `POST /api/cart/sync` + همگام‌سازی هنگام باز شدن سبد:

| وضعیت | رفتار جدید |
|---|---|
| قیمت عوض شده | قیمت قدیم خط‌خورده + نشان «افزایش/کاهش یافت» |
| موجودی < تعداد سبد | تعداد خودکار اصلاح + پیام |
| موجودی صفر | قلم کم‌رنگ + **قفل دکمه ادامه** |
| کالا حذف شده | خودکار از سبد بیرون می‌رود |

**فایل:** `src/server.js`، `public/cart.html`

### ۳. بارکد برچسب پستی جعلی بود 🔴

**علائم:** بارکد ظاهر درستی داشت اما هیچ اسکنری نمی‌خواندش.

**ریشه:** کد قبلی از روی شماره سفارش یک seed می‌ساخت و خطوطی با پهنای
**تصادفی** می‌کشید:

```js
seed = (seed * 1103515245 + 12345) >>> 0;
const w = 1 + (seed >>> 16) % 3;     // ← پهنای تصادفی
```

**رفع:** پیاده‌سازی واقعی Code128 در `public/assets/code128.js`، بدون
کتابخانه بیرونی (CDN از ایران کند/فیلتر است).

**راستی‌آزمایی سه‌لایه:**

1. **مقایسه بیت‌به‌بیت با `python-barcode`** — ۲۳ از ۲۴ مورد یکسان
2. **آن یک مورد** (`"99"`) بررسی دستی شد: خطا از کتابخانه مرجع است، نه ما.
   کتابخانه در `_try_to_optimize` عدد ۹۹ را با دستور `CODE_B` اشتباه
   گرفته و رقم کنترلی را حذف کرده. محاسبه دستی `(105 + 99) mod 103 = 101`
   خروجی ما را تأیید می‌کند.
3. **رمزگشای مستقل** — SVG تولیدشده را می‌خواند و به متن برمی‌گرداند:
   ۱۰ از ۱۰ ✓

**نکات پیاده‌سازی:**
- خروجی SVG است نه بیت‌مپ → هنگام چاپ تار نمی‌شود
- حالت C: رشته رقمی، هر دو رقم در یک نماد → بارکد باریک‌تر
- حاشیه آرام (quiet zone) لازم برای اسکن

### ۴. تیکت مرجوعی با سفارش جعلی پذیرفته می‌شد 🔴

```bash
curl -X POST /api/tickets -d '{"order_id":"XXX-JAALI", ...}'
# → 201 Created  ✗ سفارشی به این نام وجود ندارد
```

**رفع:** چهار لایه اعتبارسنجی افزوده شد:

| بررسی | پیام |
|---|---|
| سفارش وجود دارد؟ | «سفارشی با این شماره پیدا نشد» |
| ارسال/تحویل شده؟ | «مرجوعی تنها پس از تحویل مرسوله ممکن است» |
| توضیح ≥ ۱۰ حرف؟ | «دلیل مرجوعی را توضیح دهید» |
| تیکت باز تکراری؟ | «برای این سفارش تیکت باز TKT-… وجود دارد» |

هر شش سناریو تست و تأیید شد.

**فایل:** `src/server.js`

### ۵. نام محصول در فاکتور تکراری بود 🟡

**علائم:** «سمپل ۳ میل تست **3 میل**» — حجم دو بار، یکی هم با رقم لاتین.

**ریشه:** `type_label` سمپل خودش حجم را در خود داشت:

```
type      | type_label       | volume_ml
SAMPLE    | سمپل ۳ میل تست   | 3
```

کد کورکورانه `${type_label} ${volume_ml} میل` می‌ساخت.

**رفع:** تابع مشترک `variantLabel()` — اگر برچسب قبلاً «میل» داشت
دوباره اضافه نمی‌کند، و ارقام را فارسی می‌کند.

**سه نقطه اصلاح شد:** فاکتور، سبد خرید، پیامک اطلاع‌رسانی.

### ۶. شماره موبایل با فاصله رد می‌شد 🟡

کاربران معمولاً `۰۹۱۲ ۳۴۵ ۶۷۸۹` می‌نویسند. تبدیل ارقام فقط رقم را عوض
می‌کرد، فاصله باقی می‌ماند، و `/^09\d{9}$/` رد می‌کرد.

**رفع:** فاصله، خط تیره، نیم‌فاصله و ارقام عربی (`٠٩١٢`) هم پاک می‌شوند.

```
"۰۹۱۳۱۲۳۴۵۶۷"    → ✓    "0912-345-6789" → ✓
"۰۹۱۲ ۳۴۵ ۶۷۸۹"  → ✓    "٠٩١٢٣٤٥٦٧٨٩"   → ✓
```

### ۸. صفحه علاقه‌مندی راه حذف نداشت 🟡

**علائم:** برای برداشتن یک رایحه از فهرست، کاربر باید به صفحه محصول
برمی‌گشت و نشان قلب را دوباره می‌زد.

سرور از قبل حذف را پشتیبانی می‌کرد (`POST` دوباره = برداشتن)، فقط
صفحه هیچ دکمه‌ای نداشت.

**رفع:** دکمه سطل زباله روی هر کارت با **حذف خوش‌بینانه** — کارت
بلافاصله محو می‌شود و اگر سرور خطا داد برمی‌گردد. بعلاوه دکمه «افزودن
سمپل» که ارزان‌ترین حجم موجود را مستقیم به سبد می‌اندازد.

چرخه کامل تست شد: ورود با OTP ← افزودن دو رایحه ← فهرست ← حذف یکی ✓

`journal.html` یک `readerView` کامل داشت با `openArticle()` و
`showList()` — اما کارت‌ها به `/journal/{slug}` لینک می‌دادند که
`article.html` را باز می‌کند. آن سه تابع **هرگز اجرا نمی‌شدند**.

**۱,۶۳۷ کاراکتر** حذف شد (HTML + JS + CSS).

### ۱۰. هر صفحه دو نشانی داشت — محتوای تکراری برای گوگل 🔴

**علائم:** `/terms` و `/terms.html` هر دو همان صفحه را می‌دادند.
اما تنها نسخه بدون پسوند تگ `canonical` می‌گرفت:

```
/terms       → rel="canonical" href="https://yazdperfume.ir/terms"  ✓
/terms.html  → ندارد                                                ✗
```

برای گوگل یعنی دو صفحه مستقل با محتوای یکسان؛ اعتبار بین‌شان تقسیم
می‌شود و هیچ‌کدام رتبه خوبی نمی‌گیرند.

**رفع:** ریدایرکت دائمی ۳۰۱ از `.html` به نشانی رسمی، با حفظ query:

```
/terms.html      → 301 → /terms
/cart.html?x=1   → 301 → /cart?x=1
```

صفحات چاپی و فنی (`invoice`، `label`، `404`، `payment-result`)
مستثنا هستند — در پنجره جدید باز می‌شوند و ایندکس نمی‌گردند.

بعلاوه **۱۲ فایل** اصلاح شد تا لینک‌های داخلی مستقیم به نشانی رسمی
بروند و کاربر بی‌جهت ریدایرکت نخورد.

### ۱۱. sitemap نصف صفحات را جا انداخته بود 🟡

`brands`، `terms`، `privacy` و `contact` در sitemap نبودند — گوگل
راهی برای پیدا کردنشان جز پیمایش لینک‌ها نداشت.

**رفع:** هشت صفحه ثابت با `changefreq` و `priority` مناسب، و
`lastmod` برای مقالات.

`robots.txt` هم کامل شد: صفحات شخصی (سبد، حساب، علاقه‌مندی، ورود) و
چاپی (فاکتور، برچسب) از ایندکس خارج شدند.

```
۲,۱۱۹ نشانی · XML معتبر · صفر نشانی .html
۲۹۳ کیلوبایت → ۱۰.۶ کیلوبایت با gzip
```

### ۱۲. تصویر هیرو نسخه WebP نداشت و دیر کشف می‌شد 🟡

بزرگ‌ترین تصویر صفحه اصلی (۷۱ کیلوبایت) دو مشکل داشت:

۱. **نسخه WebP نداشت** — بقیه تصاویر داشتند، این یکی جا افتاده بود
۲. **داخل CSS تعریف شده بود** — مرورگر تا پس از تجزیه کامل استایل
   کشفش نمی‌کرد، پس اولین نمایش دیر می‌شد

**رفع:**

```
hero-cinematic.jpg        ۷۰,۹۵۸   (اصلی، پس‌افت)
hero-cinematic.webp       ۲۲,۹۷۴   (۶۸٪ کمتر)
hero-cinematic-sm.webp     ۶,۵۴۰   (موبایل، ۹۰۰px)
```

با `image-set()` مرورگر خودش بهترین را برمی‌دارد، و `<link rel=preload>`
با `media` جدا برای موبایل/دسکتاپ آن را زودتر شروع می‌کند.

روی موبایل: **۷۱ کیلوبایت → ۶.۵ کیلوبایت**.

### ۱۳. دارایی‌های ثابت gzip نمی‌شدند 🟡

سرور HTML و JSON را فشرده می‌کرد اما CSS و JS را نه — همان دو فایلی که
هر بازدیدکننده حتماً دانلود می‌کند.

| فایل | خام | gzip | صرفه‌جویی |
|---|---|---|---|

## بهینه‌سازی فونت

فونت کامل وزیرمتن ۸۱۱ نویسه دارد — لاتین گسترده، نمادهای ریاضی،
کسرها. سایت فارسی تنها بخشی را نشان می‌دهد.

**چرا کار خطرناکی است؟** فارسی خط اتصالی است: «ب» در «بـ»، «ـبـ»
و «ـب» سه گلیف متفاوت دارد. این شکل‌ها در `cmap` نیستند و با جدول
`GSUB` ساخته می‌شوند. اگر `layout_features` حذف شود متن به‌هم می‌ریزد.

**روش امن که پیاده شد:**

1. فهرست نویسه‌ها از **محتوای واقعی** استخراج شد — همه فایل‌های
   HTML/CSS/JS به‌علاوه نام محصول، برند، نُت و مقاله از دیتابیس.
   نه از حدس.
2. کل بلوک عربی/فارسی (U+0600–06FF) به‌عنوان حاشیه امن نگه داشته شد،
   تا محصول جدید با نویسه‌ای که امروز در دیتابیس نیست مشکل نسازد.
3. `layout_features = ['*']` تا اتصال حروف سالم بماند.
4. **راستی‌آزمایی پیکسلی:** ۶۶ متن واقعی (شامل ۱۵ نام محصول تصادفی
   از دیتابیس) با فونت اصلی و زیرمجموعه رندر و بایت‌به‌بایت مقایسه شد.

```
Regular    ۵۰,۶۸۴ → ۲۸,۶۲۸  (۴۴٪)
Bold       ۵۱,۰۲۰ → ۲۹,۰۲۰  (۴۴٪)
جمع پنج وزن ۲۵۴,۹۸۴ → ۱۴۴,۷۰۰  (۴۴٪ کمتر)

۶۶ آزمون رندر → همه پیکسل‌به‌پیکسل یکسان ✓
```

> **اشتباهی که در راه رخ داد و درسش:** بار اول فهرست نویسه‌ها را
> دستی نوشتم و `·` (U+00B7) را جا انداختم — همان جداکننده‌ای که در
> «ژیوودان · فیرمنیش» استفاده می‌شود. آزمون پیکسلی گرفتش. اگر فقط
> چشمی نگاه کرده بودم، احتمالاً متوجه نمی‌شدم.
> از آن پس فهرست از محتوای واقعی استخراج می‌شود، نه حدس.

**اسکریپت:** `scripts/optimize_fonts.py`
نسخه‌های اصلی در `assets/fonts-original/` نگهداری می‌شوند.

```bash
python3 scripts/optimize_fonts.py            # ساخت + راستی‌آزمایی
python3 scripts/optimize_fonts.py --verify   # فقط بررسی
```

اگر رندر تغییر کند، اسکریپت با کد خطا خارج می‌شود.

## باگ ۱۴ — پرداخت ناموفق موجودی را چند بار آزاد می‌کرد 🔴

**چطور پیدا شد؟** آزمون همزمانی نوشتم که ۱۰ تأیید پرداخت هم‌زمان
برای یک سفارش می‌فرستد. نتیجه تکان‌دهنده بود:

```
پاسخ موفق      : 10
وضعیت سفارش    : CANCELLED
موجودی پس از آن: +10        ← ده بار آزاد شد!
```

**ریشه:** `verifyPayment()` ناهمگام است (با درگاه گفت‌وگو می‌کند).
ده درخواست همگی از بررسی `status === 'PAID'` رد می‌شدند، در `await`
معلق می‌ماندند، و بعد **همه با هم** به مسیر شکست می‌رسیدند. هر کدام
موجودی را افزایش می‌داد.

در دنیای واقعی این یعنی: درگاه بانکی callback را دو بار می‌فرستد
(تلاش مجدد شبکه) یا کاربر صفحه پرداخت را رفرش می‌کند → موجودی
انبار شما بی‌دلیل بالا می‌رود و کالایی که ندارید «موجود» نشان
داده می‌شود.

**رفع:** قفل **پیش از** فراخوانی درگاه، نه بعد از آن:

```js
const claimed = db.prepare(
  "UPDATE orders SET status='VERIFYING', updated_at=? " +
  "WHERE order_id=? AND status='PENDING'"
).run(now, orderId);

if (!claimed.changes) return sendJSON(409, {...});  // دیگری زودتر رسید
```

`VERIFYING` وضعیت گذراست؛ در همان درخواست به `PAID` یا `CANCELLED`
می‌رود. مسیرهای موفق و ناموفق هر دو شرط `status='VERIFYING'` دارند،
پس تنها دارنده قفل می‌تواند تغییر دهد.

**پس از رفع:**

```
تأیید واقعی    : 1
«قبلاً پرداخت»  : 9      ← کد ۲۰۰، چون درگاه نباید خطا ببیند
رکورد PAID     : 1
موجودی         : بدون تغییر
```

## باگ ۱۷ — «خبرم کن وقتی موجود شد» فقط در یک حالت کار می‌کرد 🟡

مشتری روی محصول ناموجود دکمه «به من اطلاع بده» را می‌زند و شماره‌اش
ثبت می‌شود. اما موجودی از **چهار** راه می‌تواند برگردد:

| مسیر | پیش از رفع |
|---|---|
| ادمین در پنل موجودی را زیاد کند | ✓ اطلاع می‌داد |
| سفارشی که آخرین موجودی را برده لغو شود | ✗ سکوت |
| پرداخت ناموفق و بازگشت موجودی | ✗ سکوت |
| سفارش پرداخت‌نشده منقضی شود | ✗ سکوت |

سه مسیر از چهار مسیر بی‌صدا بودند. بدتر اینکه **مسیر انقضا** رایج‌ترین
است: کسی سفارش می‌دهد، پرداخت نمی‌کند، بعد از ۳۰ دقیقه موجودی
برمی‌گردد — و آن مشتری که هفته‌ها منتظر بود هیچ‌وقت خبردار نمی‌شود.

**رفع:** تابع مشترک `notifyStockWatchers(skus, reason)` که در هر چهار
نقطه صدا زده می‌شود. تنها اگر موجودی واقعاً بالای صفر باشد پیامک
می‌رود، و پس از ارسال `notified=1` می‌شود تا تکراری نرود.

**یک نکته معماری:** `releaseStaleOrders()` در `db.js` است و نمی‌تواند
`notify` را require کند (وابستگی حلقوی: notify → db). پس تابع حالا
SKUهای آزادشده را برمی‌گرداند، و `server.js` با
`setStockFreedHandler()` قلاب اطلاع‌رسانی را ثبت می‌کند.

## باگ ۱۸ — کد تخفیف بیش از ظرفیتش مصرف می‌شد 🔴

کوپنی با ظرفیت **۳** ساختم و ده سفارش هم‌زمان فرستادم:


**ریشه:** یک ناهماهنگی زمانی در طراحی. `validateCoupon` سقف را هنگام

**پرداخت** بالا می‌برد. بین این دو فاصله هست — و در آن فاصله، همه
سفارش‌ها شمارنده را صفر می‌بینند.

در عمل: کمپین «۵۰ نفر اول» را راه می‌اندازید و ۵۰۰ نفر تخفیف
می‌گیرند. اگر تخفیف درصدی روی اقلام گران باشد، ضرر واقعی است.

**رفع — کوپن مثل موجودی کالا رفتار می‌کند:**

۱. ظرفیت در لحظه **ثبت سفارش** رزرو می‌شود، نه هنگام پرداخت
۲. افزایش شمارنده اتمی است:

```sql
UPDATE coupons SET used_count = used_count + 1
WHERE UPPER(code)=? AND used_count < ?
```

اگر `changes` صفر باشد یعنی ظرفیت همان لحظه پر شده و سفارش با
`409` رد می‌شود.

۳. اگر پرداخت انجام نشود (لغو، انقضا، خطای درگاه) ظرفیت **برمی‌گردد**
   — `releaseCouponUse()` در چهار نقطه صدا زده می‌شود.

**پس از رفع:**

| سنجه | پیش | پس |
|---|---|---|
| ده سفارش هم‌زمان، ظرفیت ۳ | ۱۰ تخفیف | **۳** |
| پنج سفارش هم‌زمان یک کاربر، «یک‌بار برای هر نفر» | نامعلوم | **۱** |
| لغو سفارش | ظرفیت هدر می‌رفت | **برمی‌گردد** |

### درسی که در تست‌نویسی گرفتم

تست اول من سناریوهای ۲ و ۳ را **صفر** نشان می‌داد و فکر کردم باگ
دیگری هست. علت این بود که سناریوی اول تمام سهمیه محدودیت نرخ

اگر همان‌جا نتیجه می‌گرفتم، باگی گزارش می‌کردم که وجود نداشت. با یک
اسکریپت اشکال‌زدایی مستقل معلوم شد رزرو درست کار می‌کند.

## باگ ۱۹ — تزریق اسکریپت از راه نظرات (XSS) 🔴🔴

جدی‌ترین آسیب‌پذیری امنیتی که تا حالا پیدا شده.

نظر کاربر، نام نمایشی، تیکت مرجوعی و نام گیرنده سفارش همگی با
`innerHTML` چاپ می‌شدند **بدون هیچ خنثی‌سازی**. هیچ تابع `esc` در
سمت فرانت وجود نداشت.

**آزمون — هر پنج بار مخرب خام برگشتند:**

```
✗ <script>window.__xss=1</script>
✗ <img src=x onerror="window.__xss=1">
✗ "><svg onload=alert(1)>
✗ '><iframe src=javascript:alert(1)>
✗ <a href="javascript:alert(1)">کلیک</a>
```

نظری می‌فرستد، منتظر می‌ماند تا شما برای تأیید بازش کنید، و کد او
با **توکن ادمین شما** اجرا می‌شود: تغییر قیمت، حذف محصول، خواندن
اطلاعات مشتریان.

نیازی هم به مهارت خاصی ندارد — فرم نظر عمومی است.

### رفع در دو لایه

## باگ‌های ۲۰ تا ۲۲ — مجوزهایی که وعده می‌دادند ولی عمل نمی‌کردند 🔴

پس از ساخت سامانه نقش‌ها، بررسی کردم کدام مجوز تعریف شده ولی
هیچ‌جا سنجیده نمی‌شود:

```bash
node -e "مقایسه ALL_KEYS با can('...') در server.js"
→ ۶ مجوز بدون بررسی
```

سه‌تایشان حفره واقعی بودند:

### ۲۰. انباردار می‌توانست قیمت را عوض کند

```
انباردار: products.price ندارد
PUT /api/admin/variants/… {"price_toman": 1}
→ ۲۰۰ · قیمت ۱۹۶٬۰۰۰ → ۱ تومان
```

مسیر ویرایش کالا فقط `products.stock` را می‌سنجید، ولی همان مسیر
قیمت را هم می‌نوشت.

### ۲۱. پشتیبان می‌توانست سفارش را لغو کند

`orders.cancel` تعریف شده بود ولی مسیر تغییر وضعیت فقط
`orders.status` را می‌خواست. لغو موجودی را برمی‌گرداند و کد
تخفیف را آزاد می‌کند — کار حساسی که به پشتیبان داده نشده بود.

### ۲۲. محتوانویس فاکتور همه مشتریان را می‌دید

مسیر فاکتور با `isValidSession()` کار می‌کرد — یعنی «هر کارمند
واردشده». نام، شماره و نشانی هر مشتری برای هر کارمندی باز بود.

### قاعده‌ای که جایگزین شد

مجوز بر اساس **کاری که واقعاً انجام می‌شود** بررسی می‌شود، نه
مسیری که صدا زده شده. اگر یک مسیر دو کار با حساسیت متفاوت انجام
می‌دهد، هر کدام مجوز خودش را می‌خواهد.

### ابزار دائمی

`scripts/audit_permissions.js` — سه بررسی خودکار که نگذارد این
دوباره اتفاق بیفتد:

1. هر مجوز دست‌کم یک بار سنجیده شود
2. هیچ مسیر مدیریتی بی‌محافظ نماند
3. هیچ مجوز مرده‌ای نباشد

**اثبات شد که کار می‌کند:** یک بررسی را عمداً حذف کردم و ابزار
بلافاصله گزارشش داد. در آزمون دود اجرا می‌شود.

## باگ‌های ۲۳ تا ۲۷ — راه‌های ارتقای خودخواسته 🔴🔴

باگ‌های ۲۰ تا ۲۲ از این پرسش آمدند: «آیا هر نقش فقط کار خودش را
می‌کند؟» اما پرسش خطرناک‌تر این است: **«آیا نقش میانی می‌تواند
خودش را بالا بکشد؟»** آزمون تازه‌ای نوشتم که نقش‌های `staff.manage`
و `roles.manage` را می‌سازد و با آن‌ها به سیستم حمله می‌کند.

از ۲۱ بررسی، **۱۱ مورد شکست** — یعنی ۵ راه نفوذ باز بود.

### ۲۳. تصاحب کامل حساب مدیر کل 🔴🔴

خطرناک‌ترین. هر کارمندی که `staff.manage` داشت:

```
PUT /api/admin/staff/1   { "password": "HijackedPass1" }
→ 200 OK
```

مسیر بازنشانی رمز فقط `can('staff.manage')` را می‌سنجید و کاری
نداشت که هدف کیست. یعنی مجوز «افزودن کارمند» در عمل برابر بود با
تصاحب کل فروشگاه: رمز مدیر کل را عوض می‌کنی، با آن وارد می‌شوی،
هر ۳۲ مجوز را داری.

**این حمله در آزمون واقعاً موفق شد.** رمز مدیر کل عوض ماند و
اجرای بعدی آزمون‌ها اصلاً نتوانست وارد شود — که خودش نشان داد
باگ نظری نبوده.

**رفع:** حساب `owner` را تنها خودِ `owner` تغییر می‌دهد. تلاش
ناموفق در `audit_log` و لاگ امنیتی ثبت می‌شود.

### ۲۴. حذف و غیرفعال کردن مدیر کل

محافظت «آخرین مدیر کل» فقط وقتی به کار می‌آمد که یک نفر باقی مانده
باشد. با دو مدیر کل، کارمند `staff.manage` یکی را حذف می‌کرد، بعد
آن یکی «آخرین» می‌شد ولی خودش دیگر رفته بود.

**رفع:** حذف و غیرفعال‌سازی حساب `owner` هم مخصوص خودِ `owner` شد.

### ۲۵. ویرایش نقشِ خودِ کارمند

قید ارتقا فقط جلوی افزودن `roles.manage` و `staff.manage` را
می‌گرفت. اما کارمندی که `roles.manage` داشت می‌توانست نقش خودش را
باز کند و به جای آن دو، «خروجی CSV مشتریان» یا «تغییر قیمت»
بردارد — که برای سرقت داده یا خرابکاری مالی کافی است.

**رفع:** ویرایش نقشی که خودت عضوش هستی ممنوع شد. ویرایش نقش
دیگران باز ماند.

### ۲۶. تغییر نقشِ خودِ کارمند

کارمند با `staff.manage` نمی‌توانست خودش را `owner` کند (آن یک
مورد بررسی می‌شد)، ولی می‌توانست خودش را به هر نقش پرقدرت دیگری
منتقل کند.

**رفع:** تغییر نقش خود از هر مسیری ممنوع شد. همچنین بازنشانی رمز
خود از مسیر مدیریت کارکنان بسته شد — راهش «تغییر رمز» است که رمز
فعلی را می‌پرسد، وگرنه کسی که پشت میز باز نشسته بدون دانستن رمز
فعلی آن را عوض می‌کند.

### ۲۷. رمز اولیه در عمل رمز دائمی بود

پرچم `must_change` فقط یک پنجره در پنل باز می‌کرد. کارمند پنجره را
می‌بست و ماه‌ها با رمزی کار می‌کرد که مدیر روی کاغذ داده بود —
رمزی که دست‌کم دو نفر می‌دانند و احتمالاً در پیام‌رسان رد و بدل شده.

**رفع:** تابع `can()` پیش از هر بررسی مجوز، `must_change` را
می‌سنجد. تا تغییر رمز، سرور هیچ کاری را قبول نمی‌کند:

| مسیر | پیش از تغییر رمز |
|---|---|
| `/api/admin/login` | باز |
| `/api/admin/whoami` | باز |
| `/api/admin/change-password` | باز |
| **هر مسیر دیگر** | **۴۰۳ با `must_change: true`** |

پنل هم هماهنگ شد: تا رمز عوض نشود هیچ تبی ساخته نمی‌شود (وگرنه
کارمند صفحه‌ای پر از خطا می‌دید). پنجره دکمه «خروج از حساب» دارد
تا کسی گیر نیفتد، و بعد از تغییر رمز پنل واقعی بدون بارگذاری
دوباره ساخته می‌شود.

### درسی که ماند

آزمون قدیمی `test_rbac.js` هم باید اصلاح می‌شد: کارمندان آزمایشی‌اش
با رمز اولیه مستقیم کار می‌کردند. حالا مثل کارمند واقعی اول رمز را
عوض می‌کنند — آزمونی که مسیر واقعی کاربر را طی نکند، آن مسیر را
نمی‌سنجد.

**ابزار دائمی:** `scripts/test_rbac_escalation.js` (۲۱ بررسی) که
به آزمون دود اضافه شد. هارنسش هم اصلاح شد تا خروج زودهنگام را
«موفق» نشمارد و رمز مدیر کل را همیشه به حالت اولیه برگرداند.

`#content` در صفحه محصول با `display:none` شروع می‌شود تا کاربر
محتوای نیمه‌ساخته نبیند. اما هیچ‌جای کد دوباره روشنش نمی‌کرد.
نتیجه: صفحه محصول فقط هدر و فوتر نشان می‌داد — نه تصویر، نه قیمت،
نه دکمه خرید.

**چرا هیچ آزمونی نگرفتش:**

| بررسی | نتیجه |
|---|---|
| سرور | `200 OK` |
| عنوان صفحه | درست |
| متادیتای سئو | درست |
| خطای جاوااسکریپت | هیچ |
| HTML خروجی | کامل (محتوا در DOM بود، فقط پنهان) |

هر ۶۹ آزمون قبلی سبز بودند. سطح API چیزی برای گزارش نداشت، چون
مشکل در CSS بود نه در داده.

**چطور پیدا شد:** با نصب Chromium و نوشتن آزمون مرورگر واقعی. اولین
اجرا روی کلیک «افزودن به سبد» تایم‌اوت داد: `element is not visible`.
بررسی نشان داد **همه** دکمه‌های صفحه نامرئی‌اند.

**رفع:** دو خط در پایان `render()` — پنهان کردن اسپینر و نمایش محتوا.

### درس

آزمونی که مرورگر واقعی اجرا نکند، نمی‌فهمد صفحه برای انسان چطور
دیده می‌شود. «سرور ۲۰۰ داد» با «مشتری می‌تواند خرید کند» یکی نیست.

**ابزار دائمی:** `scripts/test_browser.py` (۱۹ بررسی با Chromium):
خطای جاوااسکریپت در ۱۴ صفحه، منابع شکست‌خورده، رندر واقعی محصولات،
سوییچ تب ویترین، سبد خرید سرتاسری، لینک‌های اجتماعی، و موبایل
(سرریز افقی و اندازه لمسی دکمه‌ها).

## تحلیل داخلی و ویترین خودکار

سه چیز که خواسته شده بود: ابزار تحلیل، بخش‌های خودکار سایت
(پرفروش‌ترین و بیشترین علاقه‌مندی)، و شبکه‌های اجتماعی.

### چرا تحلیل داخلی و نه گوگل آنالیتیکس

۱. داده مشتری ایرانی از کشور خارج نمی‌شود
۲. بدون کوکی ردیابی — نیازی به بنر رضایت نیست
۳. همان داده مستقیم به سایت برمی‌گردد و ویترین را می‌سازد
۴. هیچ اسکریپت بیرونی روی صفحه بار نمی‌شود (سرعت)

### حریم خصوصی — چه چیزی ذخیره نمی‌شود

جدول `events` این ستون‌ها را دارد: `kind`، `target`، `meta`،
`visitor`، `at`. **خبری از IP، شماره موبایل، نام یا شناسه پایدار
کاربر نیست.**

`visitor` هش SHA-256 از «IP + عامل کاربر + نمک روزانه» است. نمک
هر روز عوض می‌شود و در حافظه می‌ماند، پس:

- نمی‌توان از هش به IP رسید
- فردا همان شخص هش دیگری می‌گیرد → ردیابی در طول زمان ناممکن
- فقط برای شمردن «چند نفر جدا در امروز» به کار می‌رود

خزنده‌ها هم شمرده نمی‌شوند، وگرنه «پربازدیدترین» یعنی «چیزی که
گوگل بیشتر خزیده».

### ویترین خودکار صفحه اصلی

سه تب که از داده واقعی ساخته می‌شوند:

| تب | منبع |
|---|---|
| پرفروش‌ترین‌ها | سفارش‌های پرداخت‌شده ۹۰ روز |
| بیشترین علاقه‌مندی | جدول `wishlist` |
| پربازدید این هفته | رویداد `view` هفت روز |

**صداقت:** تا وقتی فروش واقعی ثبت نشده، عنوان «پرفروش‌ترین» نیست —
«منتخب سردبیر» است با توضیح «تا نخستین فروش‌ها ثبت شود». تبی که
داده کافی ندارد (کمتر از ۳ محصول) اصلاً ساخته نمی‌شود.

نسخه اول fallback با `MIN(id)` هر خانواده پر می‌شد و چون شناسه‌ها
به ترتیب برند وارد شده‌اند، **هر هشت محصول از یک برند درمی‌آمدند**.
حالا از هر برند حداکثر یکی: ۸ برند و ۵ خانواده متفاوت.

آمار از پیش محاسبه و در جدول `trending` ذخیره می‌شود (هر ساعت)،
پس صفحه اصلی هیچ `GROUP BY` سنگینی نمی‌زند.

### داشبورد تحلیل در پنل

مجوز تازه `reports.traffic`. مهم‌ترین بخشش **قیف خرید** است:

```
مشاهده محصول → افزودن به سبد → شروع تسویه → خرید موفق
```

هر پله درصد تبدیل از پله قبل را نشان می‌دهد و پله‌ای که زیر ۳۰٪
باشد قرمز می‌شود — یعنی همان‌جا باید درست شود.

سه گزارش دیگر:

- **جستجوهای بی‌نتیجه** — مشتری چه خواسته که نداریم
- **پرجستجوترین عبارت‌ها** — با میانگین تعداد نتیجه
- **زیاد دیده، کم فروخته** — احتمالاً قیمت یا توضیح مشکل دارد

### باگ ۳۱ — مجوز تازه به مدیر کل نمی‌رسید 🔴

هنگام افزودن `reports.traffic` معلوم شد `seedRoles()` با
`if (has) return;` شروع می‌شود: نقش‌ها فقط یک بار ساخته می‌شوند.

یعنی روی هر فروشگاهِ در حال کار، **هر مجوزی که در نسخه‌های بعدی
اضافه شود هرگز به مدیر کل نمی‌رسد** و بخش تازه برای خودِ صاحب
فروشگاه هم ۴۰۳ می‌داد.

**رفع:** نقش `owner` در هر بالا آمدن با فهرست کامل مجوزها هم‌تراز
می‌شود (طبق تعریف، مدیر کل همه‌چیز را دارد). بقیه نقش‌ها دست
نمی‌خورند — ممکن است مدیر عمداً محدودشان کرده باشد.

### شبکه‌های اجتماعی

| جا | محتوا |
|---|---|
| فوتر همه صفحات | ستون «ما را دنبال کنید» با دکمه اینستاگرام و تلگرام |
| صفحه تماس | تلگرام و اینستاگرام کنار تلفن و نشانی |
| `schema.org` | `sameAs` — به گوگل می‌گوید حساب‌های رسمی کدام‌اند |

آیدی‌ها در `SOCIAL` در `app.js` و `SOCIAL_LINKS` در `seo.js` تعریف
شده‌اند — اگر عوض شدند فقط همان دو جا تغییر کند.

**آزمون دائمی:** `scripts/test_analytics.js` (۲۲ بررسی) شامل
حریم خصوصی، نادیده گرفتن خزنده، رد رویداد جعلی، صحت رتبه‌بندی و
کنترل دسترسی.

## تصاویر محصول — از ۱۰ به ۱۸ تصویر متمایز

۲٬۱۰۶ محصول تنها ۱۰ تصویر داشتند. ۵۰۰ عطر گلی دقیقاً یک عکس مشترک
می‌گرفتند، پس کاتالوگ شبیه ده کارت تکراری پشت سر هم بود — برای
فروشگاهی با هویت لوکس، ضعف جدی.

### راه‌حل

برای هر «خانواده بویایی × جنسیت» چند واریانت بصری ساخته شد و
محصولات با **هش شناسه** بینشان پخش می‌شوند.

**چرا هش و نه شماره ردیف:** تخصیص باید پایدار باشد. با شماره ردیف،
حذف یک محصول تصویر همه محصولات بعدی را جابه‌جا می‌کرد — کش مرورگر
می‌شکست و تصاویر ایندکس‌شده گوگل عوض می‌شدند.

### قاعده بصری: بطری بی‌برچسب

محصولات ما بازآفرینی دست‌سازند، نه اصل. نمایش بطری برند اصلی هم
گمراه‌کننده است و هم از نظر حقوقی پرخطر. پس بطری خنثی و بی‌نام، با
فضاسازی برگرفته از نُت‌های همان خانواده: گلی با گل صد تومانی و
ابریشم، چوبی با تراشه سدر و سنگ خارا، عنبری با صمغ و چوب گردو.

### لوگوی برند روی هر بطری

بطری خنثی است اما بی‌هویت نیست: لوگوی «عطر یزد» روی **هر ۲۱ تصویر**
حک شده.

**چرا پردازش تصویر و نه تولید دوباره با هوش مصنوعی:** مدل تصویرساز
هرگز لوگوی دقیق برند را بازتولید نمی‌کند — هر بار شکلی نزدیک ولی
متفاوت می‌سازد. با پردازش، نقش دقیقاً همان `uploads/logo.png` است.

افکت «حکاکی روی شیشه» از سه لایه ساخته می‌شود: سایه بالا-چپ،
نور پایین-راست، و روشنایی داخل نقش. شدتش با روشنایی محل تطبیق
می‌یابد، پس روی بطری مشکی چوبی و بطری صورتی گلی هر دو درست دیده
می‌شود.

**دو باگ در همین مرحله پیدا و رفع شد:**

۱. تشخیص بدنه از کناره‌های قاب اسکن می‌کرد و گل و پارچه اطراف را
   جزو بطری می‌گرفت — عرض ۹۱۸ پیکسل یعنی تقریباً کل قاب. با اسکن
   از محور مرکزی به بیرون حل شد.

۲. در `family-floral` لوگو کنار بطری در هوا نشست. علت: بطری آن
   تصویر اصلاً وسط قاب نیست. سه محافظ اضافه شد (نسبت ارتفاع به
   عرض، محدوده عرض، فاصله از محور) و اگر رد شوند تصویر بدون لوگو
   می‌ماند — بهتر از نقش در جای غلط. مختصات آن دو استثنا دستی ثبت شد.

نسخه بدون لوگو در `assets/product-nologo/` می‌ماند و اسکریپت همیشه
از آنجا شروع می‌کند، وگرنه حکاکی روی حکاکی انباشته می‌شد.

### باگ ۳۲ — ۷۲۴ محصول تصویر شکسته گرفتند 🔴

هنگام افزودن دور دوم تصاویر، `VARIANT_COUNTS` به‌روز شد ولی خودِ
فایل‌ها در snapshot ذخیره نشدند. نتیجه: دیتابیس به ۱۰ تصویر
ناموجود اشاره می‌کرد و **۷۲۴ محصول کارت با تصویر خالی** داشتند.

سایت همچنان ۲۰۰ می‌داد، هیچ خطایی در لاگ نبود، و آزمون‌های سطح
API چیزی نمی‌دیدند — چون از نظر آن‌ها همه‌چیز درست بود.

**رفع دو مرحله‌ای:**

۱. فوری: `VARIANT_COUNTS` به تعداد واقعی فایل‌ها برگشت و
   `reassign_images.js` محصولات را به تصویر خانواده (که موجود و
   لوگودار است) بازگرداند. سایت بلافاصله سالم شد.

۲. دائمی: `test_images.js` حالا بلوک `VARIANT_COUNTS` را از
   `db.js` می‌خواند و برای هر عدد بررسی می‌کند فایلش روی دیسک
   باشد. **اثبات شد که کار می‌کند:** عدد را عمداً از ۴ به ۹ بردم و
   آزمون بلافاصله گفت «۵ فایل نیست: fam-woody-m-5.jpg».

**درس:** پیکربندی دستی که از وضعیت واقعی فایل‌ها جلو بیفتد،
بی‌سروصدا صدها محصول را خراب می‌کند. هر عدد دستی باید آزمونی
داشته باشد که با واقعیت مقایسه‌اش کند.

### نتیجه

| معیار | پیش | پس |
|---|---|---|
| تصاویر متمایز | ۱۰ | **۳۱** |
| بطری‌های لوگودار | ۰ | ۴۱ از ۴۱ |
| بزرگ‌ترین گروه هم‌تصویر | ۵۱۹ | **۱۳۴** |
| محصولات با تصویر اختصاصی | ۰ | **۲٬۱۰۳ (۱۰۰٪)** |
| حجم کارت موبایل | ۱۴۰KB | **۸٫۸KB** |

نسخه `-sm` (۴۲۰ پیکسل) برای کارت فهرست ساخته می‌شود. کارت حدود ۳۰۰
پیکسل نمایش داده می‌شود و فرستادن فایل ۱۲۵۴ پیکسلی برای صفحه‌ای با
۲۴ کارت، چند مگابایت هدر رفتن بود.

کاهش کلی از خام تا خروجی: **۹۱٪**.

### ابزارها

```bash
python3 scripts/gen_product_images.py --plan   # نقشه ۳۲ تصویر
python3 scripts/gen_product_images.py --todo   # ساخته‌نشده‌ها + پرامپت
python3 scripts/process_product_images.py      # بهینه‌سازی
node scripts/reassign_images.js --dry          # پیش‌نمایش تخصیص
node scripts/test_images.js                    # ۱۱ بررسی
```

**کار تصاویر کامل شد:** هر ۲۹ تصویر ساخته و متصل شد. تنها ۳ محصول
روی تصویر برند مانده‌اند که عمدی است — برندهای شاخص تصویر اختصاصی
خودشان را دارند.

تصاویر موقت‌اند و با عکاسی واقعی، فقط کافی است فایل‌ها در
`assets/product-nologo/` جایگزین و `apply_logo_all.py` اجرا شود —
بدون تغییر کد.

مستندات کامل: `docs/PRODUCT_IMAGERY.md`

## باگ ۳۳ — نگارش فارسی نام برندها 🔴

دو مشکل جدا که هر دو مستقیم روی فروش اثر داشتند.

### الف) املای غیررایج

مشتری ایرانی برند را با نگارش جاافتاده بازار می‌شناسد و همان را
جستجو می‌کند. «آمواژ» به‌جای «آمواج» هم غیرحرفه‌ای دیده می‌شود و هم
در جستجوی داخلی و گوگل پیدا نمی‌شود.

۱۹ برند اصلاح شد. مهم‌ترین‌ها: آمواژ→**آمواج**، کرِید→**کرید**
(حذف کسره)، نیشانه→**نیشان**، آتلیه کلن→**آتلیه کلون**،
ثمین لندن→**تامین لندن**.

**نگارش‌ها حدس نبودند:** هرکدام با جستجوی وب از فروشگاه‌های معتبر
ایرانی (عطرافشان، لیلیوم، مارسلا) راستی‌آزمایی شد. شش موردی که
پیشنهاد اولیه‌ام با بازار نمی‌خواند کنار گذاشته شدند — مثلاً
«هیستوار دو پارفوم» که نگارش رایج‌ترش «هیستویرز د پارفومز» است.

**سازگاری با گذشته:** املای قدیمی در `BRAND_ALIASES` به ایندکس
جستجو اضافه شد. جستجوی «آمواژ» همچنان ۲۶ نتیجه می‌دهد، ولی هیچ‌جا
نمایش داده نمی‌شود.

### ب) نام برند دوبار نمایش داده می‌شد

کارت محصول با `fullName()` ساخته می‌شود: «برند — نام». اما نام
محصول خودش نام برند را داشت:

```
پنهالیگونز — پنهالیگونز ابسولو
آمواج — آمواج اینترلود
```

**۹۷۶ محصول از ۲٬۱۰۶** — تقریباً نیمی از کاتالوگ.

`cleanProductName()` فقط پیشوند «برند - » را حذف می‌کرد، ولی برند
می‌توانست وسط باشد («عطر دست‌ساز **پنهالیگونز** ابسولو») یا آخر
(«عود **پنهالیگونز**»).

### دو باگ در خودِ اصلاح

**۱. اسکریپت صفر تغییر می‌داد.** حلقه پس از نخستین الگو `break`
می‌کرد چون فقط طول رشته را می‌سنجید، نه اینکه الگو منطبق شده یا
نه. با `if (!re.test(out)) continue;` حل شد.

**۲. مترادف‌ها با بازسازی ایندکس پاک می‌شدند.** نسخه اول آن‌ها را
با `UPDATE` بعد از ساخت ایندکس اضافه می‌کرد. حالا داخل خودِ
`buildSearchIndex()` هستند.

### همگام‌سازی seed — بحرانی‌ترین بخش

اصلاح دیتابیس زنده **کافی نبود**. `seed/` منبع نخستین استقرار است؛
اگر عقب بماند، فروشگاه روی Liara دوباره با املای غلط بالا می‌آید —
همان جایی که کمترین فرصت اصلاح هست.

اعمال‌شده روی seed: **۳۴۰ برند · ۹۷۶ نام · ۱٬۹۵۲ عنوان نمایشی**

`test_cold_deploy.js` حالا نگارش برندها را هم می‌سنجد. **همین
آزمون تازه یک مورد جامانده پیدا کرد** («عود پنهالیگونز») که با
الگوهای اولیه گرفته نشده بود.

**ابزار دائمی:** `scripts/test_brand_names.js` (۱۱ بررسی) شامل
تشخیص حرف عربی، حرکت‌گذاری، و تکرار برند.

مستندات: `docs/BRAND_NAMING_FA.md`

### نوار اعلان

بالای پنل، پیش از کارت‌های آمار. هر قلم دکمه است و کلیک روی آن

| رویداد | مجوز لازم | فوری؟ |
|---|---|---|
| سفارش در انتظار ارسال | `orders.view` | خیر |

| **تیکت از مهلت ۲۴ ساعته گذشته** | `tickets.view` | **بله** |
| نظر در انتظار تأیید | `reviews.moderate` | خیر |
| کالای رو به اتمام (≤۵) | `reports.stock` | اگر >۲۰ |
| **کالای ناموجود** | `reports.stock` | **بله** |
| خطای سیستم ۲۴ ساعت اخیر | `system.logs` | اگر >۱۰ |

کار فوری نوار را قرمز می‌کند تا از حالت عادی طلایی جدا شود.
هر دو دقیقه خودکار تازه می‌شود.

### نکته امنیتی: نشت اطلاعات از راه اعلان

خطر اصلی این بود که شمارش‌ها مجوز را دور بزنند. اگر انباردار
می‌فهمید «۳ تیکت مرجوعی باز است»، همان مرزی که با RBAC ساخته شد
از راه اعلان می‌شکست.

پس **هر شمارش با مجوز خودش محافظت می‌شود** و نبود مجوز یعنی آن
قلم اصلاً در پاسخ نیست — نه اینکه صفر باشد. صفر بودن هم خودش
اطلاعات است.

سرور فقط اقلام مجاز را می‌فرستد، پس فیلتر سمت مرورگر لازم نیست
و دور زدنش هم ممکن نیست.

**آزمون دائمی:** `scripts/test_notifications.js` (۱۶ بررسی) که
سه نقش می‌سازد و تأیید می‌کند انباردار اعلان تیکت نبیند، پشتیبان
اعلان موجودی نبیند، و محتوانویس هیچ‌کدام را. شمارش‌ها هم مستقیم
با دیتابیس مقایسه می‌شوند.

## باگ ۳۴ — مقالات هیچ ساختاری نداشتند 🟡

متن مقاله با `textContent` و `white-space: pre-wrap` چاپ می‌شد.
نتیجه یک توده متن بود: «بوی وتیور را چطور توصیف کنیم؟» که یک
پرسش کلیدی است، دقیقاً شبیه بقیه متن دیده می‌شد.

بررسی با مرورگر واقعی: **صفر `<h2>` و صفر `<p>`** در کل صفحه.

دو زیان داشت:

۱. خواننده نمی‌توانست مقاله را اسکن کند و پاسخ پرسشش را پیدا کند
۲. گوگل ساختار مقاله را نمی‌فهمید — بدون عنوان‌بندی، محتوا
   «تخت» ارزیابی می‌شود

### رفع بدون تغییر محتوا

تابع `renderArticle()` متن ساده را به HTML ساختاریافته تبدیل
می‌کند. قاعده تشخیص عنوان:

- خط کوتاه (زیر ۷۰ نویسه) که با «؟» تمام شود → عنوان
- خط زیر ۴۰ نویسه بدون نقطه پایانی → عنوان (مثل «نکته کاربردی»)

هیچ متنی دست‌کاری نشد؛ فقط ساختارش دیده شد. نتیجه روی مقاله
وتیور: **۴ عنوان و ۵ پاراگراف** — از جمله «نکته کاربردی» که
پرسش نیست ولی درست تشخیص داده شد.

### نکته امنیتی: گذر از textContent به innerHTML

این تغییر ذاتاً پرخطر است. هر پاره متن پیش از ترکیب از `esc()`
عبور می‌کند.

**راستی‌آزمایی شد:** مقاله‌ای با `<img src=x onerror=alert(1)>` و
`<script>window.__pwned=1</script>` ساختم و در مرورگر واقعی باز
کردم. نتیجه: صفر تگ تزریق‌شده، `window.__pwned` تعریف‌نشده، هیچ
alert اجرا نشد، و کد مخرب به‌صورت متن خام نمایش داده شد.

`test_browser.py` حالا این را دائمی می‌سنجد: نبود `<script>`،
`<iframe>`، `<object>`، `<embed>` و هر رویداد `on*` در متن مقاله.

## حساب مشتری و کارمند — بازطراحی کامل

هشت خواسته مشخص که با هم یک سامانه هویت منسجم می‌سازند.

### مشتری: از کد یکبارمصرف به حساب واقعی

پیش‌تر هیچ جدول حسابی وجود نداشت — ورود فقط با کد پیامکی بود و
هیچ چیزی از مشتری ذخیره نمی‌شد.

جدول `customers` اضافه شد با **نام کاربری = شماره موبایل**. دلیل:
یکتاست، مشتری همیشه به یادش دارد، و نیازی به فیلد جدا ندارد.

| فیلد ثبت‌نام | الزامی؟ |
|---|---|
| نام یا نام مستعار | بله |
| نام خانوادگی | خیر |
| شماره موبایل | بله |
| رمز ۸ نویسه‌ای | بله |

**نکته طراحی:** اگر حسابی از قبل با کد پیامکی ساخته شده ولی رمز
نداشته باشد، «ثبت‌نام» یعنی «رمز بگذار» — نه خطای «قبلاً ثبت شده».

### بازیابی رمز با پیامک

دو مرحله: درخواست کد، سپس تأیید و ثبت رمز تازه.

**پاسخ برای شماره ثبت‌نشده دقیقاً یکسان است** («اگر این شماره ثبت
شده باشد، کد بازیابی پیامک شد»). وگرنه مهاجم می‌توانست بفهمد چه
شماره‌هایی در سیستم هستند.

پس از بازیابی، همه نشست‌های باز جز همین یکی باطل می‌شوند — اگر
کسی رمز را دزدیده و وارد شده بود، بیرون می‌افتد.

### کارمند: کد ملی به‌عنوان نام کاربری

| مورد | پیش | پس |
|---|---|---|
| نام کاربری | حرفی دلخواه | **کد ملی ۱۰ رقمی** |
| نام | یک فیلد | نام + نام خانوادگی جدا |
| رمز اولیه | مدیر دستی وارد می‌کرد | **خودکار: موبایل بدون صفر** |
| اطلاع‌رسانی | شفاهی | **پیامک با نقش، نام کاربری، رمز** |

کد ملی یکتاست و جعل نمی‌شود؛ نام مستعار این دو ویژگی را ندارد.

ارقام فارسی و خط تیره پذیرفته می‌شوند (`۰۰۱-۲۳۴-۵۶۷۸`) — کاربر
ایرانی با کیبورد فارسی تایپ می‌کند و بدون این تبدیل، اعتبارسنجی
بی‌دلیل رد می‌کرد.

**پیامک اطلاع‌رسانی** ناهمگام فرستاده می‌شود: اگر سرویس پیامک قطع
باشد، ساخت حساب شکست نمی‌خورد و رمز موقت در پاسخ برمی‌گردد تا
مدیر دستی بدهد.

### فرم سفارش

نام و نام خانوادگی جدا شدند (برای خطاب مؤدبانه و برچسب پستی
مرتب)، ایمیل اختیاری اضافه شد، و **کد پستی الزامی شد** — بدون آن
مرسوله پستی برگشت می‌خورد.

سفارش‌های قدیمی که نام را یکجا دارند، هنگام پرکردن خودکار فرم از
روی فاصله تفکیک می‌شوند.

### درسی که در آزمون‌ها گرفتم

تغییر نام کاربری کارمند **پنج آزمون را همزمان شکست** — هر کدام
منطق ساخت کارمند را تکرار کرده بودند.

به‌جای وصله زدن به هر پنج، یک کمک‌کننده مشترک ساختم:
`scripts/lib/test_staff.js` با `makeStaff()` که کل چرخه را انجام
می‌دهد. اگر قاعده دوباره عوض شود، فقط همان یک فایل تغییر می‌کند.

**آزمون دائمی:** `scripts/test_accounts.js` (۳۳ بررسی) که هر هشت
خواسته را می‌سنجد.

## مرور نهایی پیش از افتتاح — دو شکاف امنیتی

با نگاه تازه به کل سیستم، دو مورد پیدا شد که هیچ آزمونی نمی‌گرفت
چون «خطا» نبودند — فروشگاه بی‌هیچ ایرادی کار می‌کرد.

### باگ ۳۷ — نبود هدرهای امنیتی 🔴

تنها هدر موجود `X-Content-Type-Options` بود. برای فروشگاهی که
پرداخت می‌گیرد، نبود `X-Frame-Options` یعنی **حمله کلیک‌دزدی**
ممکن است: مهاجم صفحه پرداخت را نامرئی روی سایت خودش جاسازی
می‌کند و کلیک کاربر را می‌دزدد.

افزوده شد:

| هدر | کار |
|---|---|
| `X-Frame-Options: SAMEORIGIN` | جلوگیری از جاسازی در iframe |
| `Referrer-Policy` | نشانی صفحه به سایت دیگر نشت نکند |
| `Permissions-Policy` | دوربین، میکروفون و موقعیت غیرفعال |
| `Strict-Transport-Security` | فقط پشت HTTPS |

HSTS از `x-forwarded-proto` تشخیص داده می‌شود نه `req.socket`،
چون Liara پشت پروکسی TLS است و سوکت داخلی همیشه HTTP می‌بیند.

### باگ ۳۸ — CORS باز روی مسیرهای خصوصی 🔴

`Access-Control-Allow-Origin: *` روی **همه** مسیرها ست می‌شد،
از جمله `/api/admin`, `/api/auth` و `/api/wishlist`.

یعنی سایتی که مشتری بازش کرده می‌توانست با توکن او درخواست
بفرستد و پاسخ را بخواند. کاتالوگ عمومی است و باز بودنش اشکالی
ندارد، ولی حساب و پنل نه.

**رفع:** مسیرهای خصوصی هدر `Allow-Origin` نمی‌گیرند.

### هشدار آمادگی افتتاح

مورد سومی هم پیدا شد که باگ نبود ولی ریسک واقعی داشت: اگر
اطلاعات حقوقی ناقص بماند، فاکتور بدون آن صادر می‌شود و فروشگاه
**بی‌هیچ خطایی** کار می‌کند. این نقص تا نخستین بازرسی یا شکایت
مشتری پنهان می‌ماند.

حالا اعلان پنل بررسی می‌کند و دقیقاً می‌گوید کدام فیلد ناقص است:
«مورد ناقص در اطلاعات حقوقی (شناسه ملی)». فقط به کسی نشان داده
می‌شود که `settings.edit` دارد — هشداری که گیرنده‌اش کاری از
دستش برنمی‌آید فقط نوفه است.

**آزمون:** ۸ بررسی هدر امنیتی در `smoke_test.sh` و ۵ بررسی
هشدار حقوقی در `test_notifications.js`.

## پروفایل و کارنامه شخصی کارمند

کارمند هیچ راهی نداشت ببیند خودش چه کرده. سابقه کارها فقط برای
مدیر بود و کارمند حتی نمی‌دانست شماره موبایلش در سیستم ثبت هست
یا نه.

### تب «پروفایل من»

برای **همه** کارکنان باز است — مجوز ویژه نمی‌خواهد، چون هر کس
فقط داده خودش را می‌بیند. در `TABS` با `need: []` تعریف شده و
`buildTabs()` تبی با شرط خالی را همیشه نمایش می‌دهد.

سه بخش:

| بخش | محتوا |
|---|---|
| مشخصات من | نام، نقش، تعداد مجوز، آخرین ورود، نشست فعال |
| کارنامه من | آمار ۷/۳۰/۹۰ روزه با برجسته‌های متناسب با نقش |
| ویرایش | نام و موبایل — نقش و دسترسی نه |

### آمار متناسب با نقش

انباردار «به‌روزرسانی موجودی» می‌بیند، پشتیبان «پاسخ به تیکت»،
محتوانویس «مقاله نوشته‌شده». هر کارت فقط وقتی ساخته می‌شود که
کارمند مجوز آن حوزه را داشته باشد **و مقدارش بیشتر از صفر باشد** —
«۰ پاسخ به تیکت» چیزی نمی‌گوید و فقط کارت‌های واقعی را کم‌رنگ می‌کند.

مقایسه با دیگران عمداً نیست: کارنامه ابزار خودارزیابی است، نه
تابلوی رقابت.

### دو خطر امنیتی که بسته شد

**۱. نشت فعالیت بین کارکنان.** فیلتر بر پایه `staff_id` است نه
`username` — نام کاربری ممکن است عوض شود ولی شناسه ثابت می‌ماند.
آزمون مستقیم با دیتابیس مقایسه می‌کند و تأیید می‌کند نام هیچ
کارمند دیگری در پاسخ نباشد.

**۲. ارتقای خود از راه ویرایش پروفایل.** مسیر `me/profile` فقط
`display_name` و `mobile` را می‌پذیرد. آزمون تلاش می‌کند
`role_key`، `permissions`، `active` و `must_change` بفرستد —
همه نادیده گرفته می‌شوند.

### باگ کوچک: شمارش نشست فعال

«۱۱۳ نشست فعال» نمایش داده می‌شد. پاک‌سازی منقضی‌ها درست کار
می‌کرد و همه واقعاً زنده بودند (انباشته آزمون‌های مکرر، هر کدام
۸ ساعت اعتبار) — ولی شرط `expires_at > now` نبود، پس اگر نشستی
منقضی می‌شد همچنان شمرده می‌شد و کارمند بی‌جهت نگران می‌شد که
«کسی با حساب من وارد شده».

### جزئیات نمایش

## پشتیبان‌گیری بدون راه بازگشت

پشتیبان خودکار از روز اول کار می‌کرد — هر ۲۴ ساعت، ۷ نسخه، با
`VACUUM INTO`. سه چیز کم بود:

1. **راهی برای بازیابی نبود.** داشتن پشتیبانی که بلد نیستی برگردانی،
   یعنی پشتیبان نداری.
2. **نسخه‌های خودکار قابل دانلود نبودند** — فهرست دیده می‌شد ولی
   فایل بیرون نمی‌آمد. همه روی همان دیسک دیتابیس می‌ماندند؛ اگر آن
   دیسک از دست می‌رفت، پشتیبان‌ها هم می‌رفتند.
3. **هیچ‌وقت آزمایش نشده بود.**

**افزوده شد:** `scripts/restore_backup.js` و مسیر
`GET /api/admin/backups/:file` با دکمه دانلود در پنل.

ابزار بازیابی عمداً محتاط است: فایل را پیش از هر کاری اعتبارسنجی
می‌کند، از وضعیت فعلی نسخه ایمنی می‌گیرد، تفاوت آماری را نشان
می‌دهد و تأیید می‌خواهد، و اگر جابه‌جایی شکست بخورد خودکار
برمی‌گرداند.

## حذف کامل مالیات — «قیمت اعلام‌شده = قیمت پرداختی»

**خواسته مالک فروشگاه:**

> «لازم نیست جایی اسم از مالیات و غیره بیاید. پرداختی مشتری همان مبالغی
> است که در سایت اعلام شده و نیازی به محاسبه مبلغ اضافه‌ای در فاکتور یا
> جای دیگر نیست.»

### پیش از این چه بود

سامانه یک درصد مالیات در تنظیمات نگه می‌داشت (`vat_percent`، مقدار
ذخیره‌شده در دیتابیس زنده **۹**) و در فاکتور دو سطر خاکستری چاپ می‌کرد:
«مبلغ بدون مالیات» و «مالیات بر ارزش افزوده ۹٪ — مندرج در قیمت».

مبلغ پرداختی هیچ‌وقت عوض نمی‌شد — مالیات از مبلغ *استخراج* می‌شد نه
افزوده. ولی همین که روی فاکتور مشتری چاپ می‌شد یعنی فروشگاه دارد ادعای
مالیاتی می‌کند که پشتوانه ثبتی ندارد. برداشته شد.

### چه چیزهایی پاک شد

| جا | چه بود |
|---|---|
| `src/server.js` | محاسبه `vatPct` / `vat` / `net_goods` در مسیر فاکتور |
| `src/db.js` | کلید `vat_percent` از `SHOP_DEFAULTS` |
| `public/invoice.html` | دو سطر «مبلغ بدون مالیات» و «مالیات بر ارزش افزوده» |
| `public/admin.html` | فیلد «مالیات بر ارزش افزوده (٪)» و نگاشت `sVat` |
| `data/yazd.db` | ردیف `vat_percent = 9` از جدول `settings` حذف شد |
| مستندات | README، ARCHITECTURE، API_REFERENCE، DEEP_AUDIT، GAP، AUDIT_V3 |

چون `saveSettings()` فقط کلیدهای موجود در `SHOP_DEFAULTS` را می‌پذیرد،
حذف کلید از آن‌جا یعنی حتی درخواست دستی `POST /api/admin/settings` با
`{"vat_percent":"9"}` هم دیگر چیزی ذخیره نمی‌کند. آزمون این را می‌سنجد.

### فاکتور حالا

```
جمع کالاها
− تخفیف (اگر کد داشته باشد)
+ هزینه ارسال
─────────────────
= مبلغ قابل پرداخت
```

سه سطر، نه سطری بیشتر. همان عددی که مشتری موقع پرداخت دید.

### شفافیت به مشتری

بند «پرداخت» در `/terms` یک پاراگراف گرفت:

> قیمتی که در صفحه محصول می‌بینید همان مبلغی است که می‌پردازید. هیچ
> هزینه پنهان، کارمزد یا مبلغ اضافه‌ای به سفارش شما افزوده نمی‌شود.

### آزمون نگهبان — `scripts/test_no_extra_charges.js`

۱۴ بررسی که جلوی برگشتن این موضوع را می‌گیرد:

- پویش متنی کل `src/` و `public/` برای هفت واژه ممنوع
  (`مالیات`، `ارزش افزوده`، `عوارض`، `vat_percent`، `vat_included`، `net_goods`، …)
- `totals` فاکتور دقیقاً چهار کلید دارد: `subtotal`، `discount`، `shipping`، `grand_total`
- رابطه ریاضی: `جمع − تخفیف + ارسال === پرداختی` — اگر روزی عدد ناشناسی
  وسط راه اضافه شود، این خط قرمز می‌شود
- `grand_total` فاکتور با `total_paid` واقعی سفارش یکی است
- صفحه چاپی `/invoice`، پنل `/admin` و صفحه `/checkout` هیچ واژه مالیاتی ندارند
- تزریق `vat_percent` از راه API بی‌اثر است و در دیتابیس ذخیره نمی‌شود

آزمون سرور خودش را روی پورت ۴۴۳۷ بالا می‌آورد — درس باگ ۳۶: آزمونی که به
سرور از پیش‌درحال‌اجرا وصل شود ممکن است کد کهنه را بسنجد.

به `smoke_test.sh` اضافه شد → مجموع ۸۹ بررسی.

## ممیزی جامع پیش از افتتاح — تیر ۱۴۰۵

بررسی سرتاسری با اجرای واقعی، نه مرور مستندات. سه ابزار ممیزی
تازه ساخته شد که از این پس بخشی از آزمون دودند.

### باگ ۳۹ — بسته استقرار دیتابیس آزمونی را می‌برد 🔴

`liara.json` می‌گوید `"platform": "node"`. طبق مستندات لیارا، در
این حالت **Dockerfile خوانده نمی‌شود** — `package.json` خوانده و
`npm start` اجرا می‌شود. یعنی همه محافظت‌هایی که در Dockerfile
گذاشته بودیم (کپی انتخابی فقط `src`, `public`, `seed`) بی‌اثر بود.

هیچ `.dockerignore` وجود نداشت. `.gitignore` هم کمکی نمی‌کند چون
لیارا آن را نمی‌خواند. با شبیه‌سازی بسته‌بندی تأیید شد:
`data/yazd.db` (۱۰.۸ مگابایت، **۸۲ سفارش آزمونی**) در بسته می‌رفت.

`.dockerignore` نوشته شد. بسته از ۴۰۷ به ۲۳۸ فایل کاهش یافت و
با آزمون تأیید شد که هر هشت فایل حیاتی هنوز داخل‌اند.

### باگ ۴۰ — سرور به HEAD پاسخ ۴۰۴ می‌داد 🟡

مسیریابی فقط `method === 'GET'` را می‌پذیرفت، پس هر درخواست `HEAD`
تا انتها می‌رفت و ۴۰۴ می‌گرفت. ابزارهای پایش آپ‌تایم و بررسی‌کننده‌های
لینک اول `HEAD` می‌زنند — سایت را «از دسترس خارج» گزارش می‌کردند.

طبق RFC 9110 پاسخ `HEAD` باید همان هدرهای `GET` را داشته باشد
بدون بدنه. با پوشاندن `res.write`/`res.end` حل شد. راستی‌آزمایی:
`HEAD /` حالا ۲۰۰ با صفر بایت بدنه، `GET /` همچنان ۳۱,۸۱۳ بایت.

### باگ ۴۱ — manifest با نوع اشتباه سرو می‌شد 🟡

`.webmanifest` در جدول MIME نبود، پس `application/octet-stream`
می‌رفت و کروم نادیده‌اش می‌گرفت — «افزودن به صفحه اصلی» روی
اندروید نام و آیکن برند را نشان نمی‌داد. `.xml` و `.txt` هم
اضافه شدند.

### هیچ صفحه‌ای favicon نداشت

هر ۲۳ صفحه بدون آیکن بودند؛ تب مرورگر آیکن خالی پیش‌فرض نشان
می‌داد. برای فروشگاهی با هویت لوکس نقص محسوسی است.

`scripts/make_favicon.py` نقش خطاطی لوگو را روی زمینه ابسیدین
برند (`#121212`) با حاشیه طلایی (`#C59B27`) می‌نشاند:

| فایل | کاربرد |
|---|---|
| `favicon.ico` | چندلایه ۱۶+۳۲+۴۸ برای مرورگرهای قدیمی |
| `favicon-16.png` · `favicon-32.png` | تب مرورگر |
| `apple-touch-icon.png` | ۱۸۰×۱۸۰، بدون آلفا (اپل وگرنه زمینه سیاه می‌گذارد) |
| `icon-192.png` · `icon-512.png` | نصب روی اندروید |
| `site.webmanifest` | نام فارسی، جهت RTL، رنگ برند |

نسخه ۱۶ پیکسلی در آزمون بصری با بزرگ‌نمایی، لکه‌ای خاکستری بود.
نقش باریک و عمودی است و در آن اندازه گم می‌شود. با کاهش حاشیه
به ۸٪ و افزایش کنتراست ۱.۹ برابر خوانا شد.

### CORS مسیرهای نوشتاری باز بود

`/api/orders`, `/api/reviews`, `/api/tickets`, `/api/cart`,
`/api/stock-alert`, `/api/payment` هنوز `Access-Control-Allow-Origin: *`
می‌دادند. یعنی سایت دیگری می‌توانست فرم سفارش ما را روی دامنه
خودش سوار کند. بسته شدند؛ کاتالوگ خواندنی باز ماند و با آزمون
هر دو سمت تأیید شد.

### Content-Security-Policy اضافه شد

آخرین خط دفاع در برابر XSS. `'unsafe-inline'` لازم بود چون صفحات
اسکریپت و استایل درون‌خطی دارند، ولی همچنان جلوی بارگذاری اسکریپت
از دامنه مهاجم و نشت داده به بیرون را می‌گیرد. با سه اجرای متوالی
آزمون مرورگر تأیید شد که چیزی نشکسته.

### آزمون‌ها زیر فشار حافظه شکست زنجیره‌ای می‌دادند

اول به نظر «ناپایداری تصادفی» می‌آمد، ولی یک اجرا **۹ شکست
همزمان** داد و لاگ نشان داد `ERR_CONNECTION_REFUSED` — سرور وسط
کار مُرده بود. این محیط ~۲GB حافظه دارد و Chromium بدون سقف
حافظه اجرا می‌شد.

سه اصلاح: پرچم‌های کم‌مصرف برای Chromium، تابع `run_test()` که
بین ۱۹ آزمون یک ثانیه مکث می‌دهد، و تلاش دوباره هوشمند که فقط
وقتی `ERR_CONNECTION_REFUSED` دیده شود فعال می‌گردد (تا شکستِ
محیط با شکستِ محصول اشتباه نشود). هر آزمون حالا لاگ خودش را
نگه می‌دارد.

سه اجرای پیاپی ۸۸/۸۸ بدون تلاش دوباره.

## چهار خواسته پیش از استقرار — مرداد ۱۴۰۵

### ۱. موجودی پیش‌فرض صفر

اعداد قبلی ساختگی بودند (۱۰۰، ۸۰، ۵۰۰، ۱۵۰). اگر فروشگاه با
همان‌ها باز می‌شد، مشتری کالایی می‌خرید که در انبار نیست.

هر ۱۴,۷۴۲ واریانت صفر شدند. **`seed/` هم هماهنگ شد** — وگرنه
اولین استقرار روی سرور تازه، اعداد قدیمی را برمی‌گرداند.
`import_dataset.py` و `convert_uploaded_md_dataset.py` هم اصلاح
شدند تا اگر روزی داده از نو ساخته شود، پیش‌فرض صفر بماند.

صفحه محصول با موجودی صفر دکمه «ناموجود» غیرفعال نشان می‌دهد —
با اسکرین‌شات تأیید شد.

### ۲. کنترل موجودی در پنل

هر حجم حالا یک ردیف با دکمه **−**، کادر عدد و دکمه **+** دارد.
عدد را می‌شود دستی هم تایپ کرد.

- تغییر **فوری ذخیره می‌شود** (بدون زدن دکمه ذخیره جدا)
- مکث ۴۲۰ میلی‌ثانیه‌ای: فشردن پیاپی + ده درخواست پشت هم نمی‌فرستد
- زیر صفر نمی‌رود
- اگر مشتری منتظر آن کالا بوده، پیام «✓ N نفر خبر شدند» می‌آید
- جمع موجودی محصول زنده به‌روز می‌شود
- دکمه‌ها ۳۴ پیکسل‌اند تا روی تبلت انبار قابل لمس باشند

قیمت عمداً ذخیره دستی دارد — اشتباه در قیمت گران تمام می‌شود.

**جستجوی زنده** هم اضافه شد: با تایپ دو حرف نتیجه می‌آید، بدون
زدن دکمه.

### ۳. حجم عطر مو و بادی اسپلش

هر دو ۱۵۰ میل شدند (پیش‌تر ۵۰ و ۱۰۰).

نکته‌ای که کار را ظریف می‌کرد: **SKU حجم را در خودش دارد**
(`YZD-0001-HM-050`). با تغییر حجم، SKU هم باید عوض شود وگرنه کد
با محتوا نمی‌خواند. ۴,۲۱۱ SKU تغییر کرد — ولی یک واریانت که در
سفارشی ارجاع داشت، SKU قدیمی‌اش حفظ شد تا فاکتور آن سفارش نشکند.

### ۴. پیشنهاد خودکار جستجو

با تایپ دو حرف، پنج نتیجه برتر با تصویر، نام فارسی و لاتین،
قیمت و نشان «ناموجود» زیر کادر می‌آید.

سه نکته در پیاده‌سازی:

- **مکث ۲۵۰ms** — بدون آن با هر حرف یک درخواست می‌رود
- **شماره درخواست** — پاسخ کندِ عبارت قدیمی نباید روی نتیجه تازه
  بنشیند (شرط رقابتی رایج در autocomplete)
- **ناوبری کیبورد** — بالا/پایین/Enter/Escape، با الگوی ARIA
  combobox تا صفحه‌خوان هم بفهمد

**دو باگ که فقط با مرورگر واقعی پیدا شدند:**

۱. ناوبری کیبورد اصلاً کار نمی‌کرد. ردیابی نشان داد `scrollIntoView`
   صفحه را ۸۰ پیکسل جابه‌جا می‌کرد، شنونده `scroll` آن را «حرکت
   کاربر» می‌فهمید و فهرست را می‌بست — پیش از آنکه کاربر فلش را
   بزند. حالا اسکرول فقط داخل خود فهرست انجام می‌شود.

۲. نام لاتین و نشان «ناموجود» در یک سطر قاطی می‌شدند. با
   اسکرین‌شات دیده شد؛ سه عنصر `display:block` گرفتند.

### آزمون‌ها

موجودی صفر، پنج آزمون سفارش و پرداخت را شکست — چون به کالای
موجود نیاز داشتند. راه اشتباه این بود که موجودی تولید را بالا
نگه داریم. راه درست: `scripts/lib/test_stock.js` ساخته شد تا هر
آزمون **موجودی موقت خودش را بسازد و در پایان دقیقاً برگرداند**.

آزمون نگهبان تازه: `test_stock_and_suggest.js` با ۲۲ بررسی، شامل
مرورگر واقعی برای هر دو رابط.

مجموع: **۹۰ آزمون خودکار**.

## سامانه تخفیف پیشرفته و نوار اعلان — مرداد ۱۴۰۵

دو خواسته مالک، با یک اختلاف نظر که با داده حل شد.

### بنر اسلایدی — چرا نساختیم

مالک بنر اسلایدی خودکار برای صفحه اصلی خواست. پیش از ساخت،
پژوهش‌ها را بررسی کردم و **مخالفت کردم**:

| یافته | منبع |
|---|---|
| فقط ~۱٪ کاربران روی اسلایدر کلیک می‌کنند | Notre Dame |
| ۸۴٪ همان کلیک روی اسلاید اول است | همان |
| تصویر ثابت ۴۰٪ کلیک، اسلایدر ۲٪ | Conversionista (با ردیابی چشم) |
| حذف اسلایدر → ۲۳٪ افزایش فروش | Adobe |
| حذف اسلایدر → ۲۵٪ بهبود سرعت | Dell |

علتش «کوری بنری» است: مغز کاربر هر چیزی شبیه تبلیغ را نادیده
می‌گیرد.

**دلیل فنی مخصوص این پروژه:** بنچمارک نشان داده بود CLS صفحه
اصلی ۰٫۰۰۴ است. چرخش خودکار دقیقاً همان چیزی است که این عدد را
خراب می‌کند.

مالک پیشنهاد جایگزین را پذیرفت.

### نوار اعلان تک‌پیامی

روی همان نوار موجود بالای صفحه می‌نشیند — نه نوار دوم — تا
ارتفاع صفحه عوض نشود. **CLS اندازه‌گیری‌شده: صفر.**

- چهار لحن رنگی، قابل انتخاب از پنل
- لینک داخلی با متن دلخواه
- دکمه بستن؛ تا پایان همان روز به یاد می‌ماند
- بازه تاریخ شروع و پایان
- با انتشار اعلان تازه، قبلی خودکار خاموش می‌شود
- **لینک بیرونی رد می‌شود** — وگرنه هر کسی که به پنل دسترسی
  بگیرد می‌تواند بازدیدکننده را به سایت دیگری بفرستد

### کوپن دامنه‌دار

نه ستون تازه با `ALTER TABLE` (نه بازسازی جدول — دیتابیس زنده
است):

| قابلیت | فیلد |
|---|---|
| خانواده رایحه | `scope_families` |
| برند | `scope_brands` |
| نوع محصول | `scope_types` |
| محصول مشخص | `scope_products` |
| جنسیت | `scope_gender` |
| تاریخ شروع | `starts_at` |
| سقف خرید | `max_subtotal` |
| فقط اولین خرید | `first_order_only` |
| کد اختصاصی یک مشتری | `assigned_mobile` |

**سازگاری با گذشته:** کوپن بدون دامنه دقیقاً مثل قبل روی کل
سبد کار می‌کند. چهار کوپن موجود دست‌نخورده ماندند.

**محافظت مالی:** کوپن دامنه‌دار اگر اقلام سبد در دسترس نباشد
**رد می‌شود**. دادن تخفیفِ دامنه‌دار روی کل سبد ضرر مستقیم است.

### جشنواره — تخفیف خودکار بدون کد

مشتری کاری نمی‌کند؛ تخفیف خودش اعمال می‌شود.

- همان منطق دامنه که کوپن دارد
- سقف ۹۰٪ (بالاتر معمولاً اشتباه تایپی است)
- اگر چند جشنواره شامل یک کالا شوند، **بهترین** اعمال می‌شود
  نه جمعشان — وگرنه دو جشنواره ۳۰٪ می‌شد ۶۰٪
- ساخت جشنواره بدون دامنه، تأیید دوباره می‌خواهد

### دو باگ که آزمون پیدا کرد

**۱. کوپن روی قیمت کامل حساب می‌شد.** جشنواره ۳۰٪ می‌زد و کوپن
۱۰٪ هم روی قیمت اصلی حساب می‌شد نه باقی‌مانده. آزمون نشان داد
۱۵۱٬۵۰۰ به‌جای ۱۰۶٬۰۵۰. رفع: تخفیف جشنواره روی خودِ قلم ثبت
می‌شود تا محاسبه بعدی بداند.

**۲. خودِ آزمون اشتباه بود.** بخش کوپن پس از ساخت جشنواره اجرا
می‌شد، پس مبلغ پایه عوض شده بود. بررسی «محیط تمیز است» اضافه شد.
