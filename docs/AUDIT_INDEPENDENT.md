# ممیزی مستقل — بازخوانی با چشم تازه

**تاریخ:** مرداد ۱۴۰۵ · **سند تاریخی** — عکس یک لحظه، به‌روز نمی‌شود

پس از تفکیک `server.js`، کد از نو خوانده شد — نه به‌عنوان
نویسنده‌اش، بلکه کسی که دنبال ایراد است.

**سه یافته واقعی** درآمد که **هیچ‌کدام** از ۹۹ آزمون موجود
نمی‌گرفتشان.

---

## 🔴 یافته ۱: نشت هش رمز در پاسخ API

### چه بود

```js
// src/db.js
function getStaff(id) {
  const s = db.prepare('SELECT * FROM staff WHERE id=?').get(id);
  return { ...s, … };   // ← همه ستون‌ها، شامل pass_hash و pass_salt
}
```

و سه مسیر مدیریتی خروجی‌اش را **مستقیم در پاسخ JSON** می‌گذاشتند:

```
PUT  /api/admin/me/profile
POST /api/admin/staff
PUT  /api/admin/staff/:id
```

### تأیید با آزمون واقعی

```json
{
  "staff": {
    "username": "owner",
    "pass_hash": "614f8dc760bb4b154deebc884b6f5f9a4a344481",
    "pass_salt": "25a1c0f3bb4fcd0375f0b0dd73b1bc6a"
  }
}
```

### چرا جدی است

هش `scrypt` امن است، ولی داشتنش یعنی مهاجم می‌تواند **آفلاین**
حمله فرهنگ‌لغت بزند — بدون اینکه محدودیت نرخ ورود مانعش شود.
با رمز ضعیفی مثل `yazd1404` (که هنوز پیش‌فرض است) این کار
ثانیه‌ای انجام می‌شود.

### رفع

تابع `publicStaff()` ساخته شد — همان الگوی `publicCustomer` که
از قبل وجود داشت ولی برای کارکنان معادلش نبود.

**چرا `getStaff` خودش پاک نشد:** مسیر ورود و تغییر رمز به همان
فیلدها نیاز دارند. حذف از منبع، احراز هویت را می‌شکست.

**فهرست سفید، نه سیاه:** ستون تازه‌ای که روزی به جدول اضافه شود،
خودبه‌خود بیرون نمی‌رود.

---

## 🟡 یافته ۲: سه مسیر عمومی بدون محدودیت نرخ

| مسیر | کاری که می‌کند | محافظت |
|---|---|---|
| `/api/track` | ردیف در `events` می‌نویسد | ❌ هیچ |
| `/api/tickets` | چند کوئری + `INSERT` | ❌ هیچ |
| `/api/stock-alert` | `INSERT` در `stock_alerts` | ❌ هیچ |

هر سه بدون احراز هویت‌اند و به دیتابیس **می‌نویسند**.

### اندازه‌گیری

```
۴۰ درخواست به /api/track  →  ۳۳۷ میلی‌ثانیه، همه پذیرفته
جدول events از قبل        →  ۱۰٬۲۳۹ ردیف
```

یک اسکریپت ساده می‌توانست دیسک لیارا را پر کند و آمار
«پربازدیدترین» را آلوده کند.

### رفع — سقف‌های سخاوتمندانه

```js
track:  { limit: 120, window: 60e3,      block: 5 * 60e3 }
ticket: { limit: 5,   window: 60 * 60e3, block: 60 * 60e3 }
alert:  { limit: 10,  window: 60 * 60e3, block: 30 * 60e3 }
```

سقف‌ها طوری انتخاب شدند که **کاربر واقعی هرگز نخورد**: یک بازدید
عادی حدود ۵ تا ۱۰ رویداد می‌سازد.

**نکته طراحی:** `/api/track` هنگام محدودیت **بی‌صدا** رد می‌شود
(`200` با `throttled: true`)، نه `429`. تحلیل نباید تجربه کاربر
را خراب کند.

---

## 🔴 یافته ۳: خطای بلعیده‌شده — کشف اتفاقی

هنگام رفع یافته ۲، محدودیت اعمال **نشد** با اینکه کد درست بود.
ردیابی نشان داد:

```
ERROR | server | ip is not defined | {"path":"/api/track"}
```

### ریشه

`const ip = clientIP(req)` در **هر بلوک جداگانه** تعریف شده بود
(۵ بار تکرار). بلوک‌های دیگر به آن دسترسی نداشتند.

### چرا خطرناک‌تر از خودش بود

خطا در `catch` سراسری بلعیده می‌شد و کاربر **پاسخ ۲۰۰** می‌گرفت.
یعنی:

- کد نوشته شد ✓
- `node -c` سبز داد ✓
- سرور بالا آمد ✓
- **قابلیت هرگز کار نکرد** — بی‌هیچ نشانه‌ای

اگر آزمون واقعی (۱۵۰ درخواست) نمی‌زدم، «محدودیت نرخ اضافه شد»
می‌نوشتم در حالی که هیچ محدودیتی نبود.

### رفع

`reqIP` یک بار در سطح درخواست تعریف شد.

> **درس:** «کد نوشته شد» ≠ «کد کار می‌کند». هر قابلیت تازه باید
> با رفتار واقعی سنجیده شود، نه با خواندن.

## آنچه هنوز بررسی نشده

ممیزی کامل نیست. این محورها باقی مانده‌اند:

| محور | چرا مهم |
|---|---|
| **مسیر پرداخت** | تنها بخشی که هرگز با پول واقعی آزموده نشده |
| **تراکنش‌های ناقص** | چند `INSERT` پشت هم بدون `db.transaction()` |
| **ورودی نامنتظره** | آرایه به‌جای رشته، عدد منفی، `undefined` |
| **سازگاری سرور و فرانت** | منطقی که در دو جا تکرار شده (مثل باگ `coverOf`) |

بررسی مسیر پرداخت **عمداً** به تعویق افتاد: بدون درگاه واقعی،
هر تغییری آنجا ریسک بدون بازخورد است.
