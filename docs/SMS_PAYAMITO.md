# سامانه پیامک — پیامیتو

سامانه از کاوه‌نگار به **پیامیتو** (`payamito.com`) تغییر کرد.

---

## چرا کد حدسی ننوشتم

مستندات فنی پیامیتو — نشانی دقیق وب‌سرویس و نام پارامترها — **پشت
لاگین پنل** است. صفحه `payamito.com/webservice` فقط فهرست
قابلیت‌ها را نشان می‌دهد و نمونه‌کدها با جاوااسکریپت بار می‌شوند.
فایل‌های PDF و ZIP مستندات هم از بیرون در دسترس نبودند.

سه گزینه داشتم:

| گزینه | نتیجه |
|---|---|
| حدس زدن نشانی و پارامترها | کدی که شاید کار نکند و اشکال‌یابی‌اش روی سرور استقرار انجام شود |
| صبر تا رسیدن مستندات | پروژه معطل می‌ماند |
| **لایه قابل تنظیم** | ✅ کار می‌کند، و با رسیدن مستندات فقط متغیر محیطی عوض می‌شود |

گزینه سوم انتخاب شد.

> **نکته‌ای که در آزمون کشف شد:** ابتدا یک نشانی پیش‌فرض حدسی
> (`payamito.com/api/select`) گذاشته بودم تا «کار کند». آزمون
> نشان داد این خطرناک است: با نشانی غلط، سامانه **ساکت** شکست
> می‌خورد و مدیر تصور می‌کند پیامک‌ها می‌روند. حالا نشانی خالی
> است و بررسی آمادگی صریح می‌گوید «`SMS_API_URL` تنظیم نشده».

## معماری تازه

```
              ┌─────────────┐
   otp.js ───▶│             │
              │   sms.js    │───▶ پیامیتو / کاوه‌نگار / هر سامانه
 notify.js ──▶│             │───▶ یا لاگ سرور (پیش‌فرض)
              └─────────────┘
```

پیش‌تر کد کاوه‌نگار **در دو فایل تکرار** شده بود. تغییر سامانه
یعنی دست زدن به هر دو و دو بار احتمال خطا. حالا:

| فایل | پیش | پس |
|---|---|---|
| `notify.js` | ۲۴۵ خط | **۱۱۹ خط** |
| `otp.js` | ۱۶۶ خط | **۱۲۸ خط** |
| `sms.js` | — | ۳۷۰ خط (همه منطق ارسال) |

## پیکربندی

### حداقل لازم برای پیامیتو

```bash
liara env set SMS_PROVIDER=payamito --app yazdperfume
liara env set SMS_API_URL="نشانی وب‌سرویس از پنل" --app yazdperfume
liara env set SMS_USERNAME="نام کاربری" --app yazdperfume
liara env set SMS_PASSWORD="رمز یا کلید وب‌سرویس" --app yazdperfume
liara env set SMS_SENDER="شماره خط اختصاصی" --app yazdperfume
```

> پیامیتو اجازه می‌دهد به‌جای رمز عبور، **کلید وب‌سرویس** استفاده
> کنید. امن‌تر است — رمز پنل جایی ذخیره نمی‌شود. آن را در
> `SMS_API_KEY` بگذارید.

### اگر ساختار درخواست فرق داشت

همه‌چیز قابل تنظیم است، **بدون تغییر کد**:

| متغیر | پیش‌فرض | کار |
|---|---|---|
| `SMS_AUTH_MODE` | `json` | `json` · `query` · `bearer` |
| `SMS_FIELD_TO` | `to` | نام فیلد گیرنده |
| `SMS_FIELD_TEXT` | `text` | نام فیلد متن |
| `SMS_FIELD_FROM` | `from` | نام فیلد خط ارسال |

مثال: اگر پیامیتو فیلد گیرنده را `receptor` بخواند و اعتبارنامه
را در نشانی انتظار داشته باشد:

```bash
liara env set SMS_FIELD_TO=receptor --app yazdperfume
liara env set SMS_AUTH_MODE=query --app yazdperfume
```

## دو نوع خط

فروشگاه **خط اختصاصی** دارد، ولی هر دو پشتیبانی می‌شود.

### خط اختصاصی (پیش‌فرض)

متن آزاد فرستاده می‌شود. ساده، بدون پیش‌نیاز.
❌ به شماره‌های بلک‌لیست نمی‌رسد.

### خط خدماتی اشتراکی (الگو/پترن)

```bash
liara env set SMS_OTP_PATTERN="شناسه الگو از پنل" --app yazdperfume
```

با پر شدن این متغیر، کد یکبارمصرف از مسیر الگو می‌رود: فقط
**متغیرها** فرستاده می‌شوند و متن از الگوی از پیش تعریف‌شده در
پنل ساخته می‌شود.
✅ به بلک‌لیست هم می‌رسد · ✅ رایگان با اینماد

> اگر بعداً خط خدماتی گرفتید، فقط همین یک متغیر را ست کنید.

## تفسیر پاسخ سرویس

سامانه‌های ایرانی قالب یکسانی ندارند. `looksSuccessful()` این‌ها
را می‌شناسد:

```
{"status":200}              ✓    {"status":0,"message":"..."}  ✗
{"status":"ok"}             ✓    {"success":false}             ✗
{"success":true}            ✓    {"RetStatus":-1}              ✗
{"RetStatus":1}             ✓    -10                           ✗
{"return":{"status":200}}   ✓    HTTP 500                      ✗
{"recId":123456}            ✓
1234567                     ✓
```

**در تردید، ناموفق فرض می‌شود.** پیامکی که فکر کنیم رفته ولی
نرفته، بدتر از خطای صریح است.

## بررسی سلامت

**پنل → تنظیمات → بررسی آمادگی افتتاح**

نشان می‌دهد: نام سامانه، خط ارسال، نوع خط، و چهار نویسه آخر
کلید (`••••8765`). **هیچ کلیدی کامل نمایش داده نمی‌شود.**

### چرا «بررسی کامل» برای پیامک تماس نمی‌گیرد

برای کاوه‌نگار مسیر رایگان «اعتبار حساب» وجود داشت. برای سامانه
عمومی نمی‌دانیم کدام مسیر بی‌هزینه است — زدن یک درخواست کور ممکن
است پیامک واقعی بفرستد و اعتبار مصرف کند.

پس آزمون واقعی فقط با **دکمه «پیامک آزمایشی»** انجام می‌شود که
شماره خودتان را می‌خواهد. حداکثر ۵ بار در ساعت.

## راستی‌آزمایی

```bash
node scripts/test_sms_provider.js   # ۶۸ بررسی
```

آزمون یک **سرور HTTP جعلی** بالا می‌آورد که نقش سامانه پیامک را
بازی می‌کند و درخواست‌های رسیده را ثبت می‌کند. بدون ارسال پیامک
واقعی، بدون هزینه.

می‌سنجد: هر سه قالب احراز هویت، تغییر نام فیلدها، یازده قالب
پاسخ، هر دو نوع خط، و اینکه **حتی نیمی از کلید** در خروجی نشت
نکند.

> **نکته فنی:** آزمون هر سناریو را در پروسه جدا اجرا می‌کند، چون
> `sms.js` متغیرها را هنگام بارگذاری می‌خواند. این تصمیم درستی
> است — پیکربندی نباید وسط کار عوض شود.

## آنچه از عهده شماست

۱. ورود به پنل پیامیتو → بخش وب‌سرویس
۲. برداشتن **نشانی وب‌سرویس** و **کلید** (یا نام کاربری و رمز)
۳. ست کردن متغیرها با `liara env set`
۴. پنل → تنظیمات → **بررسی کامل** → **پیامک آزمایشی**

اگر ساختار درخواست با پیش‌فرض ما فرق داشت، متغیرهای `SMS_FIELD_*`
و `SMS_AUTH_MODE` را تنظیم کنید. **هیچ تغییر کدی لازم نیست.**

> اگر مستندات را در اختیارم گذاشتید، پیش‌فرض‌ها را دقیق تنظیم
> می‌کنم تا حتی این چند متغیر هم لازم نباشد.
