## بخش ۳ — سه مشکلی که پیدا شد

### مشکل ۱ — شناسه سفارش تکراری 🔴 بحرانی

شناسه سفارش فقط از زمان ساخته می‌شود:

```js
const orderId = `YZD-${Date.now().toString(36).toUpperCase()}`;
```

`Date.now()` دقتش میلی‌ثانیه است. **دو سفارش در یک میلی‌ثانیه،
شناسه یکسان می‌گیرند** و دومی با خطای پایگاه‌داده رد می‌شود:

```
UNIQUE constraint failed: orders.order_id
```

مشتری فقط این را می‌بیند: `{"error":"خطای داخلی سرور"}`

**نرخ شکست اندازه‌گیری‌شده** (۱۰۰ سفارش در هر ردیف، محدودیت
نرخ موقتاً برداشته شد تا خودِ موتور سنجیده شود):

| خریدار همزمان | موفق | خطای ۵۰۰ | نرخ شکست |
|---|---|---|---|
| ۱ | ۱۰۰ | ۰ | **۰٪** |
| ۲ | ۷۸ | ۲۲ | **۲۲٪** |
| ۳ | ۷۳ | ۲۷ | ۲۷٪ |
| ۵ | ۶۵ | ۳۵ | ۳۵٪ |
| ۸ | ۶۳ | ۳۷ | ۳۷٪ |
| ۱۲ | ۶۹ | ۳۱ | ۳۱٪ |
| ۲۰ | ۶۵ | ۳۵ | ۳۵٪ |

آزمون مستقیم دو سفارش همزمان:

```
خریدار اول: 201 {"order_id":"YZD-MS4MSMI0", ...}
خریدار دوم: 500 {"error":"خطای داخلی سرور"}
```

**چرا تا حالا دیده نشده بود:** همه آزمون‌های موجود سفارش‌ها را
پشت سر هم می‌فرستند، نه همزمان. مسئله فقط با بار موازی ظاهر
می‌شود.

**اثر تجاری:** از دومین خریدار همزمان به بعد، حدود یک‌سوم
سفارش‌ها گم می‌شوند. مشتری پول نداده ولی سبدش را از دست داده و
پیام مبهم دیده. در یک کمپین یا ساعت شلوغ، این یعنی از دست دادن
مستقیم فروش.

**رفع پیشنهادی:** افزودن جزء تصادفی به شناسه، یا تلاش دوباره
هنگام تداخل. کار کوچکی است ولی چون تغییر در مسیر پرداخت است،
باید با آزمون همزمانی اختصاصی همراه شود.

> ⚠️ در این بنچمارک **هیچ تغییری در کد اعمال نشد**. تنها یک
> تغییر موقت برای اندازه‌گیری زدم (بالا بردن سقف محدودیت نرخ)
> که بلافاصله برگردانده شد. کد فعلی دقیقاً همان کد پیش از
> بنچمارک است.

### مشکل ۲ — پرش چیدمان در صفحه محصول 🟡

`CLS = ۰.۷۵` روی موبایل، هفت‌ونیم برابر آستانه گوگل.

علت دقیق (با ردیابی رویدادها):

```
جابه‌جایی ۰.۷۳۱ در ۱۵۴ms  ←  DIV
```

در `public/product.html` خط ۲۰۸:

```html
<div id="content" style="display:none">
```

صفحه اول با ارتفاع صفر رندر می‌شود، بعد داده می‌رسد و `#content`
ناگهان ظاهر می‌گردد — کل صفحه یک‌باره جابه‌جا می‌شود. مشتری
درست وقتی می‌خواهد روی «افزودن به سبد» بزند، دکمه از زیر
انگشتش فرار می‌کند.

مجله هم همین مشکل را دارد (`CLS = ۰.۴۳`).

**رفع پیشنهادی:** جای خالی از پیش رزرو شود (اسکلت بارگذاری با
ارتفاع ثابت) به‌جای `display:none`.

### مشکل ۳ — LCP کند روی ۳G 🟡

روی شبکه کند، صفحه محصول ۶.۳ ثانیه طول می‌کشد تا عکس اصلی
بیاید. عنصر LCP شناسایی شد:


عکس بعد از رسیدن داده بارگذاری می‌شود، یعنی زنجیره‌ای است:
HTML → JS → API → عکس. روی ۳G هر حلقه گران است.

**نکته:** بخشی از این با رفع مشکل ۲ خودبه‌خود بهتر می‌شود، چون
اگر ساختار از اول رندر شود، مرورگر می‌تواند عکس را زودتر شروع
کند.

## بخش ۵ — رفع سه مشکل (همان روز)

هر سه مورد رفع و با همان ابزاری که پیدایشان کرد راستی‌آزمایی شد.

### ۱. شناسه سفارش تکراری — رفع شد ✅

```js
// پیش:  فقط زمان، دقت میلی‌ثانیه
const orderId = `YZD-${Date.now().toString(36).toUpperCase()}`;

// پس:   زمان + ۴ نویسه تصادفی رمزنگاری‌شده + تضمین دیتابیس
function newOrderId() {
  const t = Date.now().toString(36).toUpperCase();
  const A = 'ABCDEFGHIJKLMNOPQRSTUVWXYZ0123456789';
  const b = crypto.randomBytes(4);
  let r = '';
  for (let i = 0; i < 4; i++) r += A[b[i] % A.length];
  return `YZD-${t}-${r}`;
}
```

بخش تصادفی ۳۶⁴ = ۱٬۶۷۹٬۶۱۶ حالت در هر میلی‌ثانیه می‌دهد. آزمون
تولید ۲۰۰ هزار شناسه: از ۱۹۹٬۹۲۳ برخورد به ۲۳ رسید.

ولی ۲۳ هم صفر نیست. چون نتیجه‌اش از دست رفتن سفارش مشتری است،
یک بررسی سبک روی کلید اصلی هم اضافه شد که تا سه بار تلاش می‌کند.
این بررسی **پیش از رزرو کوپن** انجام می‌شود، چون رزرو به شماره
سفارش گره می‌خورد.

**نرخ شکست پیش و پس:**

| خریدار همزمان | پیش | پس |

| ۱ | ۰٪ | ۰٪ |

### ۲. پرش چیدمان — رفع شد ✅

اینجا چند لایه داشت و هر لایه با ردیابی رویداد `layout-shift`
پیدا شد، نه با حدس.

**ریشه اصلی — هدر.** ردیابی نشان داد `MAIN#main: y 0 → 97`.
هدر با جاوااسکریپت از `app.js` تزریق می‌شود؛ تا آن لحظه ارتفاعش
صفر است و با ظاهر شدن، **کل صفحه ۹۷ تا ۱۰۳ پیکسل پایین می‌پرد**.
این تک‌ریشه در هر ۱۸ صفحه بود.

```css
.hdr-reserve { min-height: 103px }
@media (max-width: 860px) { .hdr-reserve { min-height: 97px } }
```

**لایه‌های دیگر:** `#content` صفحه محصول، `#grid` و `#feature`
مجله، `#bg` برندها، `#houseGrid` اسانس‌ها — همه عناصری که خالی
شروع می‌شوند و با داده پر می‌شوند. برای هرکدام ارتفاع واقعی
اندازه‌گیری و رزرو شد. مقادیر **درون‌خطی** هم گذاشته شد، چون تا
رسیدن CSS چند میلی‌ثانیه فاصله است و همان کافی است تا جابه‌جایی
ثبت شود.

**فونت.** `font-display: swap` باعث می‌شد متن دوبار رندر شود.
دو کار: فونت جایگزین با متریک استخراج‌شده از خود وزیرمتن
(`ascent-override: 102.54%`)، و تغییر به `font-display: optional`.
وزن Medium هم که فقط دو استفاده داشت حذف شد (۲۸KB صرفه‌جویی).

**نتیجه CLS:**

### ۳. LCP روی شبکه کند — بهتر شد، کامل نه ⚠️

سه اصلاح:

| کار | اثر |
|---|---|
| preload تصویر محصول با WebP از سمت سرور | تصویر موازی با HTML دانلود می‌شود |
| `<picture>` برای تصویر اول گالری | با فایل preload شده یکی می‌شود |
| بندانگشتی‌ها و کارت‌ها با نسخه `-sm` | ۱۰۲KB → ۱۶KB برای هر تصویر |
| حذف preload فونت | پهنای باند به تصویر می‌رسد |

**درس گران‌بها:** اول فقط preload اضافه کردم و LCP **بدتر شد**
(۶٫۳۵ → ۷٫۱۶s). ردیابی شبکه نشان داد چرا — مرورگر WebP را
preload می‌کرد ولی جاوااسکریپت تگ تصویر را با پسوند jpg می‌ساخت،
پس دو فایل دانلود می‌شد. **preload تنها وقتی کار می‌کند که نشانی
دقیقاً یکسان باشد.**
