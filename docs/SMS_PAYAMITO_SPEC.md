# وب‌سرویس پیامک — آنچه از مستندات فهمیدیم

**تاریخ بررسی:** ۱۴ مرداد ۱۴۰۵
**منبع:** `docs.payamak-panel.com` و `melipayamak.com/api`

> **این سند زنده است** و پس از نخستین ارسال واقعی به‌روز می‌شود.

---

## خلاصه در یک نگاه

مستنداتی که فرستادید مربوط به پلتفرم **payamak-panel** است — همان
زیرساختی که پیامیتو، ملی پیامک، فراپیامک و چند سامانه دیگر رویش
سوار شده‌اند. یعنی قرارداد فنی برای همه یکسان است و تنها
اعتبارنامه و شماره خط فرق می‌کند.

**خبر خوب:** لایه پیامک ما (`src/sms.js`) از ابتدا مستقل از
ارائه‌دهنده نوشته شده و بیشتر چیزی که لازم است از قبل هست.

**خبر مهم:** یک فرض من غلط بود. حدس زده بودم پاسخ سرویس
`JSON` استاندارد است؛ در واقع این پلتفرم قالب خاص خودش را دارد
و **مهم‌تر از همه: خطاها با HTTP 200 برمی‌گردند.**

---

## دو راه ارتباط — کدام را انتخاب کنیم

| | SOAP | REST |
|---|---|---|
| نشانی | `api.payamak-panel.com/post/Send.asmx` | `rest.payamak-panel.com/api/SendSMS/SendSMS` |
| قالب | XML با پاکت SOAP | فرم ساده یا JSON |
| نیاز به کتابخانه | بله (تولید Client از WSDL) | خیر |
| مناسب پروژه ما | ❌ | ✅ |

**انتخاب: REST.**

دلیل: این پروژه عمداً تنها یک وابستگی npm دارد. افزودن یک
کتابخانه SOAP برای کاری که با ۳۰ خط کد شبکه ساده انجام می‌شود،
خلاف همان اصلی است که تا اینجا رعایت شده. ضمناً SOAP نیازمند
ساخت و نگهداری XML دستی است — سطح خطای بیشتر بدون هیچ سودی.

## قرارداد دقیق ارسال ساده

```
POST https://rest.payamak-panel.com/api/SendSMS/SendSMS
Content-Type: application/x-www-form-urlencoded

username=...&password=...&to=09123456789&from=5000...&text=متن
```

| پارامتر | الزامی | توضیح |
|---|---|---|
| `username` | ✅ | نام کاربری پنل |
| `password` | ✅ | **ApiKey** بخش تنظیمات وب‌سرویس، نه رمز ورود |
| `to` | ✅ | شماره گیرنده؛ چند شماره با کاما |
| `from` | ✅ | شماره خط اختصاصی |
| `text` | ✅ | متن پیامک |
| `isflash` | ❌ | پیامک فلش |

### پاسخ

```json
{ "Value": "recId یا کد خطا", "RetStatus": 1, "StrRetStatus": "Ok" }
```

**قاعده تشخیص موفقیت:** اگر `Value` عددی **بیش از ۱۵ رقم** باشد،
ارسال موفق بوده و آن عدد `recId` است. هر عدد کوچک، **کد خطاست**.

---

## 🔴 مهم‌ترین نکته مستندات

> «بسیاری از خطاهای کاربردی داخل بدنه پاسخ و همراه **HTTP 200**
> برمی‌گردند؛ بنابراین فقط وضعیت HTTP را معیار موفقیت قرار ندهید.»

این دقیقاً همان تله‌ای است که کد فعلی ما در آن می‌افتاد. تابع
`looksSuccessful()` در نهایت به کد وضعیت HTTP برمی‌گشت — یعنی
«نام کاربری اشتباه است» را **موفق** می‌شمرد.

نتیجه در عمل: مدیر فکر می‌کرد پیامک‌ها می‌روند، مشتری هیچ کدی
دریافت نمی‌کرد، و هیچ خطایی هم در لاگ نبود.

## جدول کدهای خطا

| کد | معنا | چه باید کرد |
|---|---|---|
| `> ۱۵ رقم` | ✅ موفق (`recId`) | — |
| `0` | نام کاربری یا رمز اشتباه | اعتبارنامه را بررسی کنید |
| `2` | اعتبار کافی نیست | شارژ کنید |
| `3` | محدودیت ارسال روزانه | تا فردا صبر کنید |
| `4` | محدودیت حجم ارسال | با پشتیبانی تماس |
| `5` | شماره فرستنده معتبر نیست | `SMS_SENDER` را بررسی کنید |
| `6` | سامانه در حال به‌روزرسانی | بعداً تلاش کنید |
| `7` | متن حاوی کلمه فیلترشده | متن را بازنویسی کنید |
| `9` | ارسال از خط عمومی با وب‌سرویس ممنوع | خط اختصاصی لازم است |
| `10` | کاربر فعال نیست | با پشتیبانی تماس |
| `11` | ارسال نشده | تلاش دوباره |
| `12` | مدارک کاربر کامل نیست | احراز هویت پنل |
| `14` | متن حاوی لینک است | لینک را بردارید |
| `16` | شماره گیرنده یافت نشد | شماره را بررسی کنید |
| `17` | متن پیامک خالی است | خطای برنامه |
| `18` | شماره گیرنده نامعتبر | قالب شماره |
| `35` | شماره در لیست سیاه مخابرات | خط خدماتی لازم است |
| `-110` | **الزام استفاده از ApiKey به‌جای رمز** | از تنظیمات وب‌سرویس ApiKey بگیرید |
| `-109` | الزام تنظیم IP مجاز | IP سرور لیارا را در پنل ثبت کنید |
| `-108` | IP به دلیل تلاش ناموفق مسدود شد | با پشتیبانی تماس |

سه کد منفی آخر مهم‌اند: یعنی پنل ممکن است **رمز ورود را نپذیرد**
و ApiKey جداگانه بخواهد، و ممکن است IP سرور را هم بخواهد.

## کد ورود یکبارمصرف — دو راه

### راه یکم: متد `SendOtp` (ساده‌تر)

```
POST /api/SendSMS/SendOtp
username, password, to, from, code
```

سامانه خودش متن را می‌سازد. نیازی به الگو نیست.

### راه دوم: خط خدماتی اشتراکی `SendByBaseNumber3`

```
POST /api/SendSMS/BaseServiceNumber
username, password, text=@bodyId@arg1;arg2, to
```

الگو (پترن) از قبل در پنل ساخته و تأیید می‌شود. `bodyId` شناسه
همان الگوست و آرگومان‌ها با `;` جدا می‌شوند.

**چرا این راه مهم است:** پیامک تبلیغاتی از خط اختصاصی به شماره‌های
داخل **لیست سیاه مخابرات** نمی‌رسد (کد خطای ۳۵). خط خدماتی
اشتراکی این محدودیت را ندارد.

برای کد ورود این حیاتی است: مشتری که در لیست سیاه باشد، هرگز
نمی‌تواند وارد حسابش شود.

## آنچه از شما لازم است

سه قلم از پنل پیامیتو، بخش **وب‌سرویس**:

| مورد | کجا |
|---|---|
| نام کاربری | همان که با آن وارد پنل می‌شوید |
| **ApiKey** | تنظیمات وب‌سرویس — **نه رمز ورود** |
| شماره خط اختصاصی | بخش خطوط |

و یک پرسش که پاسخش مسیر را تعیین می‌کند:

**آیا خط خدماتی (اشتراکی) هم دارید یا فقط خط اختصاصی؟**

اگر خط خدماتی دارید، کد ورود باید از آن برود تا به مشتریان داخل
لیست سیاه هم برسد. در آن صورت `bodyId` الگو را هم لازم داریم.

### احتمال نیاز به IP مجاز

کد خطای `-109` می‌گوید ممکن است پنل بخواهد IP سرور را از قبل
ثبت کنید. اگر چنین تنظیمی در پنل دیدید، پس از استقرار روی لیارا
باید IP اپ را آنجا وارد کنید.

## آنچه من انجام می‌دهم

پس از دریافت اعتبارنامه:

1. بازنویسی `sendGeneric` برای قالب `form-urlencoded`
2. تشخیص موفقیت بر پایه `RetStatus` و طول `recId` — نه HTTP
3. ترجمه هر ۱۹ کد خطا به پیام فارسی قابل فهم
4. پیاده‌سازی `SendOtp` و در صورت وجود خط خدماتی، `BaseServiceNumber`
5. آزمون با پاسخ‌های ساختگی برای هر کد خطا
6. `test-sms` پنل که پیام واقعی خطا را نشان دهد

**نکته صادقانه:** تا نخستین پیامک واقعی ارسال نشود، هیچ‌کدام از
این‌ها «آزموده» نیست. می‌توانم رفتار را با پاسخ ساختگی بسنجم، ولی
تأیید نهایی یک پیامک واقعی به موبایل شماست.
