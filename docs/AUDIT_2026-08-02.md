# ممیزی مستقل — ۱۱ مرداد ۱۴۰۵

ممیزی با چشم تازه روی چیزهایی که در چهار مرحله اخیر اضافه شدند و
هنوز بازبینی مستقل نشده بودند: پروفایل بویایی، فیلتر نُت، کارت
دسترسی، و PWA.

**روش:** هر ادعا با اجرای واقعی سنجیده شد، نه با خواندن کد.

## 🔴 یافته ۱ — قیمت کهنه در HTML کش‌شده

### ادعایی که نقض شد

سند `PWA.md` می‌گفت: «هرگز قیمت یا موجودی کهنه نشان نده». این ادعا
از راه API درست بود — همه مسیرهای `/api/` مستثنا شده بودند.

**ولی از راه دیگری نقض می‌شد.**

### اثبات

صفحه محصول قیمت را در **HTML سمت سرور** دارد (داده ساختاریافته
سئو، `offers.price`). سرویس‌ورکر صفحات HTML را با راهبرد
network-first کش می‌کرد.

آزمون واقعی:

```
۱) بازدید از /perfume/creed-erolfa   → کش شد
۲) قیمت در دیتابیس: ۱۹۶٬۰۰۰ → ۹۹۹٬۰۰۰
۳) بازدید آفلاین از همان صفحه
   → HTML کش‌شده همچنان ۱۹۶۰۰۰ داشت  ✗
```

### شدت واقعی

کاربر عدد را **نمی‌دید**: بخش نمایش قیمت با جاوااسکریپت از API پر
می‌شود و آفلاین شکست می‌خورد. ولی:

- خزنده گوگل همان HTML را می‌خواند
- ابزارهای اشتراک‌گذاری (تلگرام، واتس‌اپ) پیش‌نمایش می‌سازند
- برای فروشگاهی که موضعش شفافیت قیمت است، این ریسک ارزش نگه
  داشتن ندارد

### رفع

`/^\/perfume\//` به `NEVER_CACHE` اضافه شد. صفحه محصول از شبکه
می‌آید یا اصلاً نمی‌آید.

```
پس از رفع: کش‌شده: هیچ ✓
```

## 🔴 یافته ۲ — سایت به کاربر دروغ می‌گفت

### نشانه

کاربر آفلاین روی صفحه محصولی که **قبلاً دیده بود**:

> **محصول یافت نشد**
> این رایحه در کاتالوگ موجود نیست.

محصول کاملاً موجود بود. سایت داشت دروغ می‌گفت.

### علت ریشه‌ای

```js
try {
  const r = await fetch('/api/products/' + slug);
  if (!r.ok) throw 0;
  ...
} catch {
  // همه‌چیز → «محصول یافت نشد»
}
```

یک `catch` سه حالت کاملاً متفاوت را یکی می‌کرد: **نبود شبکه**،
**نبود محصول**، **خطای سرور**.

### چرا مهم است

مشتری فکر می‌کند محصول حذف شده و دیگر برنمی‌گردد. این بدتر از
نشان دادن صفحه آفلاین است — چون اطلاعات غلط می‌دهد، نه اینکه
اطلاعات ندهد.

### رفع

سه حالت تفکیک شدند، هر کدام با پیام و راه‌حل خودش. به‌علاوه
`navigator.onLine` پیش از درخواست بررسی می‌شود و شنونده `online`
صفحه را خودکار بازمی‌گرداند.

```
پس از رفع: «اتصال برقرار نشد — اتصال اینترنت خود را بررسی کنید»
           + دکمه تلاش دوباره
```

## 🟠 یافته ۳ — مسیر گران بدون محدودیت

### اندازه‌گیری

`/api/taste/suggest` کل جدول ۲٬۱۰۶ محصولی را می‌خواند و برای هر
ردیف امتیاز حساب می‌کند:

| مسیر | زمان |
|---|---|
| `/api/products?limit=24` | ۲.۵ms |
| `/api/taste/suggest` | **۵۰ms** |

**بیست برابر گران‌تر**، بدون هیچ محدودیتی.

```
۴۰ درخواست موازی در ۲.۲ ثانیه — همه پذیرفته شدند.
```

روی لیارا با دو هسته، ارزان‌ترین راه از پا درآوردن سرور.

### رفع

```js
taste: { limit: 30, window: 60e3, block: 0 }
```

**چرا `block: 0`:** این مسیر مثل ورود یا سفارش نیست که تلاش مکرر
نشانه حمله باشد. کاربر عادی ممکن است چند تب باز کند. سقف هست،
مجازات نیست — پس از پایان پنجره یک‌دقیقه‌ای بلافاصله کار می‌کند.

نسخه اول `block: 5 * 60e3` داشت که خودم در آزمون به آن خوردم و
پنج دقیقه قفل شدم. همان تجربه نشان داد برای کاربر واقعی هم بد
است.

```
پس از رفع: ۳۰ پذیرفته · ۱۵ محدود ✓
```

## 🟡 یافته ۴ — خواندن، نوشتن بود

### نشانه

```
GET /api/taste/profile     → رکورد مشتری می‌ساخت
DELETE /api/taste/profile  → رکورد مشتری می‌ساخت
POST /api/taste/suggest    → رکورد مشتری می‌ساخت
```

`resolveCustomerId()` که برای رفع باگ قبلی نوشته شده بود، رکورد را
در صورت نبود **می‌سازد**. من آن را در هر چهار مسیر گذاشته بودم،
بدون توجه به اینکه سه‌تایشان فقط می‌خوانند.

### چرا مهم است

- کاربری که با پیامک وارد شده و هرگز کوییز نداده، ردیف بی‌فایده
  می‌گیرد
- برای DELETE بی‌معناست: چیزی که نیست، پاک شدنی نیست
- اصل کلی: **GET نباید عوارض جانبی داشته باشد**

### رفع

فقط مسیر ذخیره پروفایل (`POST /api/quiz` با کاربر واردشده) رکورد
می‌سازد. بقیه از `getCustomer()` استفاده می‌کنند که فقط می‌خواند.

```
پس از رفع: GET + suggest + DELETE → هیچ رکوردی ساخته نشد ✓
           کوییز → رکورد ساخته شد ✓
```

## 🟡 یافته ۵ — جدولی که فقط رشد می‌کرد

### نشانه

```
audit_log   ۱۹٬۳۰۲ ردیف   ← هیچ پاک‌سازی خودکاری نداشت
events      ۱۳٬۳۷۸ ردیف   ✓ روزانه پاک می‌شود
app_logs    ۱۹٬۵۳۶ ردیف   ✓ ۳۰ روز
sessions       ۱۴۸ ردیف   ✓ با انقضا
```

تابع `purgeAudit()` نوشته شده، صادر شده، و در `server.js` وارد شده
بود — ولی **هیچ‌جا صدا زده نمی‌شد**.

### نرخ رشد

```
۳٬۱۰۰ ردیف در روز (نرخ آزمون)
در یک سال: بیش از یک میلیون ردیف
```

نرخ تولید کمتر خواهد بود، ولی سقف نداشتن روی دیسک محدود لیارا دیر
یا زود مشکل‌ساز می‌شود.

### رفع

به همان زمان‌بند روزانه `analytics.purge()` اضافه شد.

مدت نگهداشت از `AUDIT_KEEP_DAYS` می‌آید — **۹۰ روز**، همان
قراردادی که از قبل در `FILE_INDEX.md` مستند شده بود.

نکته حین رفع: نسخه اولم ۳۶۵ روز را تحمیل می‌کرد و قرارداد مستند
را نادیده می‌گرفت. خودِ `purgeAudit()` پیش‌فرض را درست مدیریت
می‌کند، پس عددی تحمیل نمی‌شود.

## ✅ آنچه بررسی شد و سالم بود

### منطق مالی — دقیق

```
۲ × ۱۹۶٬۰۰۰ = ۳۹۲٬۰۰۰  (subtotal)
+ ۲۵۰٬۰۰۰                (ارسال یزد)
= ۶۴۲٬۰۰۰                (total_paid) ✓
```

هیچ مبلغ اضافه‌ای. موجودی درست رزرو شد (۷۸ → ۷۷).

### احراز هویت — محکم

| آزمون | نتیجه |
|---|---|
| توکن جعلی → `/api/taste/profile` | `authenticated: false` ✓ |
| توکن جعلی → DELETE | ۴۰۱ ✓ |
| توکن جعلی → ساخت رکورد | هیچ ✓ |

### مستثناسازی سرویس‌ورکر — بی‌نقص

۲۲ مسیر آزموده شد، همه مطابق انتظار. حتی حالت‌های مرزی مثل
`/accounts-page` و `/labelling` درست مسدود می‌شوند (محافظه‌کارانه،
که برای کش درست است).

### مقاومت در برابر داده خراب

پروفایل بویایی با شش نوع داده خراب (JSON نامعتبر، آرایه، `null`،
مقدار ناشناس، رشته ۵۰۰ نویسه‌ای) آزموده شد. **هیچ استثنایی پرتاب
نشد** — همه به شیء خالی یا `null` تبدیل شدند.

### فیلتر نُت — کارآمد

۴۰ درخواست موازی به `/api/notes` در ۰.۵ ثانیه. فیلتر با چهار شرط
`EXISTS`: ۵ میلی‌ثانیه. ایندکس درست کار می‌کند.

### ایندکس نُت — بدون خطر ناهمگامی

هیچ مسیر API به جدول `products` نمی‌نویسد، پس ایندکس نُت نمی‌تواند
از داده واقعی عقب بیفتد. ابزار بازسازی دستی هم موجود است.

## درس تکرارشونده

هر پنج یافته **بی‌صدا** بودند:

- سرور ۲۰۰ می‌داد
- هیچ خطایی در لاگ نبود
- همه آزمون‌های موجود سبز بودند

یافته دوم (پیام دروغ) از همه آموزنده‌تر است: کدی که کاملاً کار
می‌کرد، در شرایطی که هیچ‌کس نیازموده بود، **اطلاعات غلط** می‌داد.

> «کد کار می‌کند» ≠ «کد در همه شرایط حقیقت می‌گوید»

## آنچه هنوز ممیزی نشده

**مسیر پرداخت با پول واقعی** — همچنان بزرگ‌ترین ریسک باقی‌مانده.
کد نوشته و با درگاه آزمایشی تست شده، ولی این با تراکنش واقعی یکی
نیست. پس از اتصال زرین‌پال، حتماً یک خرید واقعی کم‌مبلغ.

**PWA روی HTTPS واقعی** — اینجا روی `localhost` آزموده شد که
مرورگرها استثنا می‌کنند. پس از استقرار، نصب را با گوشی واقعی
امتحان کنید.

**رفتار زیر بار واقعی** — بنچمارک‌ها تک‌کاربره‌اند. رفتار با ۵۰
کاربر هم‌زمان روی دیسک شبکه‌ای لیارا ناشناخته است.
