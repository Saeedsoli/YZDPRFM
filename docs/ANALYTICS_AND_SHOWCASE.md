# تحلیل داخلی و ویترین خودکار

راهنمای کامل سامانه تحلیل، بخش‌های خودکار صفحه اصلی، و شبکه‌های
اجتماعی.

---

## خلاصه

| مورد | وضعیت |
|---|---|
| ابزار تحلیل | داخلی، بدون سرویس بیرونی |
| کوکی ردیابی | ندارد |
| داده شخصی ذخیره‌شده | هیچ (نه IP، نه موبایل، نه نام) |
| ویترین خودکار | سه تب از داده واقعی |
| به‌روزرسانی | هر ساعت، خودکار |
| مجوز لازم برای داشبورد | `reports.traffic` |
| آزمون | ۲۲ بررسی خودکار |

---

## چرا داخلی و نه گوگل آنالیتیکس

۱. **داده مشتری ایرانی از کشور خارج نمی‌شود.**
۲. **بدون کوکی ردیابی** — نیازی به بنر رضایت نیست.
۳. **همان داده به سایت برمی‌گردد** — پرفروش‌ترین و محبوب‌ترین از
   همین رویدادها ساخته می‌شوند، نه از فهرست دستی.
۴. **سرعت** — هیچ اسکریپت بیرونی روی صفحه بار نمی‌شود.

## حریم خصوصی

جدول `events` فقط این ستون‌ها را دارد:

| ستون | محتوا |
|---|---|
| `kind` | نوع رویداد (`view`، `search`، …) |
| `target` | شناسه محصول یا عبارت جستجو |
| `meta` | JSON کوتاه (مثلاً تعداد نتیجه) |
| `visitor` | هش روزانه |
| `at` | زمان |

**آنچه ذخیره نمی‌شود:** نشانی IP، شماره موبایل، نام، ایمیل، شناسه
پایدار کاربر.

### شناسه بازدیدکننده

```
visitor = SHA256(IP + عامل کاربر + نمک روزانه)[:16]
```

- نمک هر روز عوض می‌شود و **فقط در حافظه** می‌ماند
- با ری‌استارت سرور هم عوض می‌شود
- از هش نمی‌توان به IP رسید (یک‌طرفه)
- فردا همان شخص هش دیگری می‌گیرد → **ردیابی در طول زمان ناممکن**

تنها کاربردش شمردن «چند نفر جدا در امروز» است.

### خزنده‌ها

بازدید ربات‌ها شمرده نمی‌شود. بدون این، «پربازدیدترین» یعنی «چیزی
که گوگل بیشتر خزیده» نه «چیزی که مشتری بیشتر دیده».

الگوی تشخیص: `bot`، `crawler`، `spider`، `slurp`، `bingpreview`،
`headless`.

## رویدادهایی که ثبت می‌شوند

| رویداد | کجا ثبت می‌شود | چطور |
|---|---|---|
| `view` | سرور | هنگام درخواست `/api/products/:slug` |
| `search` | سرور | هنگام جستجو، فقط صفحه اول |
| `add_cart` | مرورگر | `YazdCart.add()` |
| `checkout` | مرورگر | باز شدن صفحه تسویه |
| `purchase` | **سرور** | پس از تأیید پرداخت |
| `wishlist` | سرور | افزودن به علاقه‌مندی |
| `quiz` | مرورگر | تکمیل کوییز |

**چرا خرید سمت سرور:** رویداد خرید مبنای «پرفروش‌ترین» است. اگر از
مرورگر می‌آمد، هر کسی می‌توانست با یک درخواست ساده محصولی را
«پرفروش» کند.

هر نوع دیگری که فرستاده شود دور ریخته می‌شود (`ok: false`).

## ویترین خودکار صفحه اصلی

سه تب که خودکار ساخته می‌شوند:

| تب | منبع داده | بازه |
|---|---|---|
| پرفروش‌ترین‌ها | سفارش‌های پرداخت‌شده | ۹۰ روز |
| بیشترین علاقه‌مندی | جدول `wishlist` | همیشه |
| پربازدید این هفته | رویداد `view` | ۷ روز |

### صداقت در نمایش

- تبی که کمتر از ۳ محصول داشته باشد **اصلاً ساخته نمی‌شود**
- اگر هیچ تبی داده نداشته باشد، **کل بخش پنهان می‌ماند**
- تا وقتی فروش واقعی نباشد، عنوان «پرفروش‌ترین» نیست:

  > **منتخب سردبیر**
  > گلچینی از خانواده‌های بویایی مختلف — تا نخستین فروش‌ها ثبت شود.

### گلچین پیش‌فرض

وقتی فروشی نبوده، از هر برند حداکثر یکی انتخاب می‌شود و بین
خانواده‌های بویایی چرخانده می‌شود.

> نسخه اول با `MIN(id)` هر خانواده پر می‌شد. چون شناسه‌ها به ترتیب
> برند وارد شده‌اند، هر هشت محصول از یک برند درمی‌آمدند — ویترینی
> که شبیه تبلیغ یک برند بود. حالا ۸ برند و ۵ خانواده متفاوت.

### کارایی

آمار در جدول `trending` از پیش محاسبه و ذخیره می‌شود:

- یک بار هنگام بالا آمدن سرور
- سپس هر ساعت (`SHOWCASE_REFRESH_HOURS`)
- یا دستی از پنل: **تحلیل بازدید ← به‌روزرسانی ویترین**

صفحه اصلی پربازدیدترین صفحه است و نباید هر بار سه `GROUP BY` سنگین
بزند.

## داشبورد پنل مدیریت

تب **«تحلیل بازدید»** — مجوز `reports.traffic`.

### قیف خرید

مهم‌ترین بخش. نشان می‌دهد مشتری کجا رها می‌کند:

```
مشاهده محصول → افزودن به سبد → شروع تسویه → خرید موفق
```

هر پله درصد تبدیل از پله قبل را نشان می‌دهد. پله‌ای که **زیر ۳۰٪**
باشد قرمز می‌شود — همان‌جا بزرگ‌ترین نشتی است.

### گزارش‌ها

| گزارش | چه می‌گوید |
|---|---|
| جستجوهای بی‌نتیجه | مشتری چه خواسته که نداریم — راهنمای خرید بعدی |
| پرجستجوترین عبارت‌ها | با میانگین تعداد نتیجه |
| زیاد دیده، کم فروخته | احتمالاً قیمت یا توضیح محصول مشکل دارد |
| بیشترین علاقه‌مندی | تقاضای بالقوه |
| روند روزانه | بازدیدکننده جدا در هر روز |

## شبکه‌های اجتماعی

| حساب | آیدی |
|---|---|
| اینستاگرام | `@yazdperfume` |
| تلگرام (پشتیبانی) | `@yazdperfume_admin` |

### کجا نمایش داده می‌شوند

| جا | شکل |
|---|---|
| فوتر همه صفحات | ستون «ما را دنبال کنید» با دکمه و آیکون |
| صفحه تماس | کنار تلفن و نشانی — تلگرام بالاتر چون سریع‌ترین راه است |
| `schema.org` | `sameAs` در JSON-LD صفحه اصلی |

`sameAs` به گوگل می‌گوید این حساب‌ها متعلق به همین فروشگاه‌اند. در
پنل دانش گوگل نمایش داده می‌شوند و از جعل هویت برند جلوگیری می‌کند.

### تغییر آیدی

فقط دو جا:

```
public/assets/app.js  →  const SOCIAL = { ... }
src/seo.js            →  const SOCIAL_LINKS = [ ... ]
```

## متغیرهای محیطی

```
SHOWCASE_REFRESH_HOURS=1     # فاصله تازه‌سازی ویترین (پیش‌فرض ۱ ساعت)
ANALYTICS_KEEP_DAYS=180      # نگهداری رویدادها (پیش‌فرض ۱۸۰ روز)
```

رویدادهای قدیمی‌تر روزی یک بار پاک می‌شوند تا جدول بزرگ نشود.

## مسیرهای API

| مسیر | روش | مجوز | کار |
|---|---|---|---|
| `/api/showcase` | GET | عمومی | داده ویترین صفحه اصلی |

## آزمون

```bash
node scripts/test_analytics.js
```

۲۲ بررسی:

- ثبت رویداد و نادیده گرفتن ۴ نوع خزنده
- نبود IP و موبایل در داده (بررسی با regex روی محتوای خام)
- هش بودن شناسه بازدیدکننده و تفکیک بازدیدکنندگان
- رد رویداد جعلی و نرسیدن آن به دیتابیس
- محاسبه قیف خرید و منطقی بودن درصدها
- صحت رتبه‌بندی نزولی ویترین
- صداقت `fallback` وقتی فروشی نیست
- ۴۰۱ بدون ورود و ۴۰۳ بدون مجوز
- مهاجرت خودکار مجوز تازه به مدیر کل

در آزمون دود اجرا می‌شود.
