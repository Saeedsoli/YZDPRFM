# پشتیبان‌گیری و بازیابی ایمن

**سفارش‌ها و اطلاعات مشتریان را حفظ کنید.** هر فایل پشتیبان محرمانه است و نباید در Git یا پیوند عمومی قرار بگیرد. نسخه روی همان دیسک، جای نسخه خارج از سرور را نمی‌گیرد.

## پشتیبان‌گیری

سرور ابزار پشتیبان SQLite و دانلود مدیریتی دارد. پشتیبان خودکار ابتدا در پوشه موقت خصوصی ساخته و از نظر سلامت و جدول‌های ضروری بررسی می‌شود؛ سپس بدون بازنویسی منتشر می‌شود. نگهداری دوره‌ای فقط فایل‌های خودکار سالم با نام معتبر را شامل می‌شود و فایل مشکوک یا خراب را حذف نمی‌کند. اگر فایل همان ساعت خراب باشد جایگزین خودکار نمی‌شود و خطا ثبت می‌شود. دانلود نسخه‌های قدیمی فقط فایل مستقل با نام و سربرگ SQLite معتبر را می‌پذیرد؛ این کنترل اولیه جای آزمون کامل بازیابی را نمی‌گیرد. وضعیت، دسترسی و فضای دیسک واقعی باید در همان محیط عملیاتی بررسی شود؛ موفقیت آزمون محلی به معنی آزمون سرور واقعی نیست.

## بازیابی بدون بازنویسی

ابزار `scripts/restore_backup.js` فقط پشتیبان SQLite مستقل را در **فایلی که وجود ندارد** بازیابی و با `integrity_check` و SHA-256 بررسی می‌کند:

```bash
node scripts/restore_backup.js --list
node scripts/restore_backup.js --to-new /path/to/backup.db /path/to/new-isolated-restore.db
```

این ابزار جایگزینی دیتابیس جاری، بازنویسی مقصد موجود، فایل زنده به‌عنوان منبع و منبع با فایل‌های جانبی SQLite را رد می‌کند. حالت قدیمی `--yes` برای بازنویسی غیرفعال است. پیش از انتخاب هر مسیر، از خاموش و مستقل بودن منبع مطمئن شوید؛ از این ابزار به‌عنوان راهکار تعویض دیتابیس در حال کار استفاده نکنید.

برای پشتیبان‌های تفاضلی، ابزار زیر نیز فقط مقصد جدید می‌سازد و هش و سلامت را کنترل می‌کند. قالب پایه و دلتا و بازیابی از آرشیو در `SQLITE_DELTA_BACKUP.md` توضیح داده شده است:

```bash
python3 scripts/sqlite_delta_backup.py restore --base <full.sqlite.xz> --delta <delta.zip> --output <new-isolated.sqlite>
```

بازگردانی روی سرویس واقعی ممکن است سفارش‌های پس از زمان پشتیبان را از دست بدهد. پیش از هر تصمیم عملیاتی، سرور را از نوشتن ایمن متوقف کنید، پشتیبان تازه مستقل بگیرید و اختلاف سفارش‌ها را بررسی کنید؛ هیچ جایگزینی خودکار در این پروژه مجاز نیست.

## تأیید

`python3 scripts/test_destructive_tool_guards.py` محافظ‌های حذف، بازنویسی و بازیابی در فایل جدید را روی دیتابیس‌های موقت می‌آزماید. این آزمون و بازیابی‌های محلی، **بازیابی واقعی سرور لیارا نیستند**.

### آماده‌سازی جداول مرجوعی حساب کاربری

در فروشگاه موجود، این مهاجرت تنها به‌صورت صریح و با **توقف کامل سرویس و نویسنده‌ها** انجام می‌شود؛ کد جدید به‌تنهایی آن را بر دیتابیس موجود اعمال نمی‌کند. پس از آزمون بازیابی پشتیبان مستقل، با Node 22 و مسیرهای امن اجرا کنید:

```sh
node src/return-store-cli.js --db /path/to/existing.sqlite --backup /path/to/new-private-backup.sqlite --offline-confirmed
```

مقصد پشتیبان باید فایل جدید باشد. ابزار پیش از تغییر، پشتیبان مستقل SQLite می‌سازد و ساختار و محتوای همه جدول‌ها را مقایسه می‌کند. اطلاعات سفارش، حجم یا زمان تحویل قدیمی را حدس نمی‌زند. این مرحله به‌تنهایی قابلیت مرجوعی را در رابط یا API فعال نمی‌کند. پشتیبان روی همان دیسک جای پشتیبان خارج سرور را نمی‌گیرد.
