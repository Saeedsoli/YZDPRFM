# پشتیبان‌گیری و بازیابی

> داشتن پشتیبانی که بلد نیستی برگردانی، یعنی پشتیبان نداری.
> این سند هر دو طرف را پوشش می‌دهد.

---

## خلاصه

| | |
|---|---|
| پشتیبان خودکار | هر ۲۴ ساعت (`BACKUP_INTERVAL_HOURS`) |
| نگهداری | ۷ نسخه آخر (`BACKUP_KEEP`) |
| محل | `data/backups/` کنار دیتابیس |
| روش | `VACUUM INTO` — نسخه سازگار حتی حین نوشتن |
| حجم هر نسخه | حدود ۶ مگابایت |

---

## پشتیبان‌گیری

### خودکار

سرور ۳۰ ثانیه پس از بالا آمدن اولین نسخه را می‌گیرد، سپس هر ۲۴ ساعت.
اگر در همان ساعت نسخه‌ای موجود باشد، دوباره نمی‌گیرد.

```
data/backups/yazd-2026072518.db
                  └─┬──┘└┬┘└┬┘
                  تاریخ  روز ساعت
```

### دستی از پنل

**پنل مدیریت ← ابزارها ← دانلود پشتیبان دیتابیس**

فهرست نسخه‌های خودکار هم همان‌جاست و هر کدام دکمه دانلود دارد.

### ⚠ نکته مهم

نسخه‌ها **روی همان دیسکی** ذخیره می‌شوند که دیتابیس روی آن است.
اگر آن دیسک از دست برود، پشتیبان‌ها هم می‌روند.

**دست‌کم یک نسخه را بیرون نگه دارید** — روی رایانه خودتان یا فضای
ابری. برای این کار از دکمه دانلود در پنل استفاده کنید.

## بازیابی

### فهرست نسخه‌های موجود

```bash
node scripts/restore_backup.js --list
```

```
  3 نسخه پشتیبان:

   1. yazd-2026072518.db     6.0 MB  2026-07-25 18:21  2106 محصول · 8 سفارش
   2. yazd-2026072418.db     6.0 MB  2026-07-24 18:20  2106 محصول · 6 سفارش
   3. yazd-2026072318.db     5.9 MB  2026-07-23 18:19  2104 محصول · 4 سفارش
```

اگر نسخه‌ای خراب باشد، همین‌جا با رنگ قرمز مشخص می‌شود.

### بازگرداندن

```bash
node scripts/restore_backup.js data/backups/yazd-2026072518.db
```

ابزار پیش از هر تغییری:

1. **نسخه پشتیبان را اعتبارسنجی می‌کند** — `integrity_check` به‌علاوه
   بررسی وجود جدول‌های ضروری. اگر فایل خراب باشد یا دیتابیس دیگری
   باشد، کاری نمی‌کند و دیتابیس فعلی دست‌نخورده می‌ماند.

2. **تفاوت را نشان می‌دهد:**

   ```
                       فعلی        پشتیبان
   محصول               2106  =        2106
   سفارش                 11  →           8   (-3)

   ⚠ هشدار: 3 سفارش از دست می‌رود.
     این سفارش‌ها پس از گرفتن این پشتیبان ثبت شده‌اند.
   ```

3. **تأیید می‌خواهد** — باید «بله» بنویسید. با `--yes` رد می‌شود.

4. **نسخه ایمنی می‌گیرد** — وضعیت فعلی در
   `data/pre-restore-<زمان>.db` ذخیره می‌شود.

5. **پس از جابه‌جایی تأیید می‌کند** — اگر آمار نخواند، خودکار
   وضعیت قبلی را برمی‌گرداند.

سپس **سرور را ری‌استارت کنید**.

### برگرداندن خود بازیابی

اگر پس از بازیابی پشیمان شدید، پیام پایانی مسیر نسخه ایمنی را
می‌دهد:

```bash
node scripts/restore_backup.js data/pre-restore-2026-07-25182333.db --yes
```

## آزمون فاجعه — انجام‌شده

سناریوی کامل اجرا و تأیید شد:

| گام | نتیجه |
|---|---|
| ۳ سفارش تازه پس از پشتیبان ثبت شد | ۱۱ سفارش |
| دیتابیس با داده بی‌معنا بازنویسی شد | `file is not a database` |
| بازیابی از پشتیبان | ✓ ۲,۱۰۶ محصول · ۱۴,۷۴۲ متغیر |
| سایت پس از ری‌استارت | ۲۰۰ ✓ |

آزمون‌های محافظتی:

| ورودی | رفتار |
|---|---|
| فایل خراب | رد شد، دیتابیس دست‌نخورده |
| SQLite معتبر ولی بدون جدول‌های ما | رد شد با پیام مشخص |
| نسخه قدیمی‌تر با سفارش کمتر | هشدار «۵ سفارش از دست می‌رود» |

امنیت مسیر دانلود:

| تلاش | پاسخ |
|---|---|
| بدون توکن مدیر | `401` |
| پیمایش مسیر `../../src/server.js` | `400` |
| نام دلخواه `yazd.db` | `400` |
| فایل ناموجود | `404` |

تنها نام‌هایی با الگوی `yazd-\d{10}\.db` پذیرفته می‌شوند.

## متغیرهای محیطی

```bash
BACKUP_INTERVAL_HOURS=24    # فاصله پشتیبان خودکار
BACKUP_KEEP=7               # تعداد نسخه نگهداری‌شده
DB_PATH=/app/data/yazd.db   # روی Liara
```

روی Liara، `data/backups/` داخل دیسک پایدار قرار می‌گیرد و با
ری‌استارت پاک نمی‌شود — به شرطی که دیسک به `/app/data` متصل باشد.

## توصیه عملیاتی

- **ماهی یک بار** یک بازیابی آزمایشی روی محیط محلی انجام دهید.
  پشتیبانی که هرگز آزمایش نشده، پشتیبان نیست.
- پیش از هر تغییر بزرگ (ورود دسته‌ای محصول، تغییر قیمت گروهی)
  دستی یک نسخه بگیرید.
- نسخه‌های `pre-restore-*.db` را پس از اطمینان از نتیجه پاک کنید؛
  در `.gitignore` هستند ولی فضای دیسک می‌گیرند.
